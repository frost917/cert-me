# B06 3단계 잔여 작업지시서

기준일: 2026-10-05 · 기준 HEAD: `5b0e809`

## 실행 중 결정

이하 표는 착수 당시 gap 기록이다. 사용자가 최초 설정 경로 제안을 승인해 `POST /api/v1/setup/settings`를 구현했다. 관리자 세션+CSRF, `pki_required`·설정 없음, 전체 필드 명시 입력, 초기 version 1, 기존 설정 충돌/GET 확인으로 확정했다. 기존 PR 질문 보류 지시는 이 승인으로 해소됐다. 실행 브랜치는 `codex/b06-stage3-completion`이며 실제 완료/검증 증거는 구현 문서와 TDD 증거 보고를 기준으로 갱신한다.

## 확인 결과와 범위

로그인/로그아웃/세션 조회/reset 완료, CSRF, Settings GET/PATCH, setup 완료, HTML/HTMX는 이미 구현되어 있다. 이 기능 전체를 다시 구현하지 않는다. 아래는 **실제 미구현**과 **구현됐으나 미검증**을 구분한 작업지시다.

| 항목 | 현재 상태 / 근거 | 처리 |
| --- | --- | --- |
| 최초 설정 생성 | 미구현. `SettingsService.Get/prepareUpdate`는 행이 없으면 `settings_not_configured`; Create/Initialize command와 HTTP route 없음 | S3-01 계약 결정 이후 S3-04 구현 |
| 첫 service_url 입력 화면 | 미구현. `web/app.js:loadSettings`는 설정 없음 안내 후 form을 숨김 | S3-04와 함께 연결 |
| HTTP 인증·설정 경계 테스트 | 미검증. `internal/adapter/http`에 테스트 파일 없음 | S3-02 우선 |
| runtime/브라우저 초기 흐름 | 미검증. `internal/runtime`에 테스트 파일 없음; 브라우저 증거 없음 | S3-03 |
| 네 DB 장애·경쟁 | 미검증. 외부 3종 schema 검사는 DSN 부재 skip | S3-05. 2단계 검증 잔여도 함께 추적하되 3단계 기능 미구현으로 혼동하지 않음 |
| Root 생성 화면/API | 4단계 범위. 현재 없어서 setup 완료 E2E 의존성이 남음 | 4단계 담당과 통합 gate 조정; 3단계로 임의 이동하지 않음 |

## S3-01 · 최초 설정 계약 결정 — 루트

산출물은 최초 설정을 입력할 경로·method·request/response·초기 version/재시도·인증/CSRF·설치 상태 제한을 정리한 계약 제안이다. 첫 service_url을 관리자 명시 입력으로 받고 고정 settings 행 생성과 감사 기록의 transaction을 정의한다. bootstrap TLS와 canonical URL 검증 관계, 이미 설정된 설치의 재요청 처리, 동시 최초 생성의 패자 응답을 명시한다.

**기존 사용자 지시대로 최초 입력 경로는 PR 질문으로 남긴다. 경로 결정 전 S3-04는 대기한다.** 요청 Host, 임의 URL 또는 암묵적 PATCH upsert로 대체하지 않는다. 제안은 기존 API/보안/수명 주기/저장 문서와 비교하고 승인된 결정만 OpenAPI 생성기에 반영한다.

## S3-02 · 기존 HTTP 경계 회귀 테스트 — Luna worker

소유 파일: `internal/adapter/http/*_test.go` 신규 파일. production·공유 contract/service/runtime 파일을 직접 수정하지 않는다. 테스트에서 발견한 결함은 RED 증거와 최소 수정 제안으로 루트에 전달한다.

표준 testing/httptest와 좁은 application fake를 사용하고 호출 횟수/전달 command로 거절 시 미호출을 검증한다. 다음 보장별로 독립 테스트를 작성한다.

- pre-auth/session/자동 CSRF mode, 유효 세션 필요 조건, Origin/Referer/Sec-Fetch-Site 허용·거절, 변경된 canonical origin에서 이전 pre-auth 토큰 거절.
- 로그인 성공 cookie의 Secure/HttpOnly/SameSite/Path, 자동 로그인 없는 첫 관리자 생성, 로그아웃 cookie 제거, 로그인 실패 정보 비노출, 429와 Retry-After 및 내부 timestamp 제외.
- mutation에 Origin·CSRF 누락/불일치가 있으면 변경 service 미호출. 인증 실패 시 상태·cookie 처리가 계약과 일치.
- Settings의 If-Match 누락 428, malformed 거절, version 전달/ETag, unknown/null/nested 필드 검증, 설정 행 없음 오류 유지.
- setup 완료에 settings version 전달, Root 없는 service 오류의 HTTP 매핑. 실제 Root 조건은 기존 service 테스트와 함께 증명.
- URL 게시의 역순 완료/동시 실행에서 최신 version 유지. 단순 pointer 구현을 복제하지 말고 후속 origin 검증에 적용된 URL로 관측.

기존 기능이 처음부터 통과하는 회귀 테스트에는 RED를 invent하지 않는다. 결함 발견 시에만 해당 재현 테스트 RED → checkpoint → 최소 fix → 동일 target GREEN을 수행한다. 비밀번호/토큰은 테스트 실패 메시지에 출력하지 않는다.

## S3-03 · runtime 및 브라우저 검증 — Luna tester

읽기/검증 역할이며 production 수정 금지. S3-02 이후 실행한다. 실제 임시 SQLite/격리된 fixture로 bootstrap → 관리자 생성 → 로그인 → settings 없음 오류를 확인한다. 기존 설정 fixture에서는 settings 조회/수정 → setup Root 없음 거절을 확인한다. fixture를 신규 설치 성공으로 표시하지 않는다.

브라우저에서는 reset token이 서버 HTML에 복사되지 않고 URL/history에서 제거되는지, pre-auth 선택, cookie/session 상태, HTMX CSP/local 자산, 설정 없음 안내를 검증한다. 브라우저 도구가 없으면 미실행으로 보고하고 대체 단위 테스트를 E2E로 표시하지 않는다. runtime 테스트 추가가 필요하면 worker에 별도 파일 소유권을 배정한다.

## S3-04 · 최초 설정 service/HTTP/UI — 계약 확정 후 Luna worker

S3-01 확정 전 착수하지 않는다. service → HTTP → UI의 작은 TDD 단위로 분리하고 공유 port/storage 변경은 루트가 통합한다. 명시 입력·URL/TLS 검증·최신 세션/CSRF 권한·고정 행 생성 경쟁·감사의 원자성과 rollback을 검증한다. 기존 Settings Update의 version 정책과 기존 delivery/series 기한 불변조건을 보존한다.

완료 증거: 행 없는 DB에서 승인된 요청으로 정확히 한 settings 행 생성, 동시 생성/응답 손실 재시도에 계약된 결과, 이후 GET/PATCH 정상 동작, UI에서 입력→저장→version 수신, 오류 시 비밀/부분 결과 미노출. OpenAPI와 관련 문서를 함께 갱신한다.

## S3-05 · DB 검증·독립 검토·종료 — Luna tester / Astra reviewer / 루트

SQLite와 제공된 PostgreSQL/MySQL/MariaDB 전용 테스트 DSN에서 최초 설정 경쟁·version·rollback·세션/CSRF transaction 재검사를 수행한다. DSN 값은 출력하지 않는다. DSN 없는 DB는 skip/미검증으로 기록한다. Astra가 실제 변경 diff의 인증·origin·최초 설정 원자성과 API 호환성을 읽기 전용 검토한다.

루트는 기본 gate `python3 tools/check_artifacts.py`, `go test ./... -v`, `go vet ./...`와 관련 race/coverage를 실행한다. gofmt/goimports 및 사용 가능한 gosec를 적용하고 없는 도구는 기록한다. `golang-patterns`, `golang-testing`, `tdd-workflow`, 보안 수정 시 `security-review`, API 변경 시 `api-design`을 사용한다. TDD checkpoint와 실제 RED/GREEN/coverage/skip 증거를 보존한다.

## 완료 판정과 4단계 연결

S3-02/S3-03은 최초 설정 계약을 기다리지 않고 진행 가능하다. 통과 후 명시적 validity를 사용하는 CA 생성·조회 연결을 4단계에서 진행할 수 있다. **3단계 완전 완료**는 S3-04와 신규 설치 입력 흐름까지 구현·검증한 뒤 판정한다. Root 생성과 setup 완료를 포함한 전체 여정은 4단계 결과와 통합해 검증한다. 완료되지 않은 항목과 외부 DB 검증 공백은 `3-구현사항.md`에 남긴다.

이번 산출물은 작업지시서다. 구현/테스트 코드를 변경하거나 새 검증 결과를 주장하지 않는다.
