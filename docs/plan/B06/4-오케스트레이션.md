# B06 3단계 점검과 4단계 착수 계획

기준일: 2026-10-09 · 3단계 완료 기준: `a1e1ac1` · 상태: 완료

## 3단계 현재 상태

`docs/implement/개발단계/B06/3-구현사항.md`와 실제 HTTP/runtime 코드를 대조했다. 로그인·로그아웃·세션 조회·비밀번호 reset 완료, pre-auth/session CSRF, Settings GET/PATCH와 setup 완료, 로컬 HTML/HTMX 화면이 연결되어 있다. 설정 URL snapshot은 version/CAS로 게시한다.

후속 3단계 보완에서 사용자 승인에 따라 `POST /api/v1/setup/settings`와 최초 입력 화면을 구현했다. 기존 Settings Update는 기존 행 수정이며 요청 Host나 임의 기본값으로 초기화하지 않는다. HTTP 회귀 테스트와 실제 SQLite HTTPS/SQL runtime의 생성·경쟁·rollback·재시작 검증도 추가했다. 최종 네 DB 결과는 3단계 구현/TDD 증거 문서를 따른다. Root 생성 route는 4단계 범위이므로 Root API를 포함하는 신규 설치 E2E 통과를 아직 선언하지 않는다.

## 착수 판정

**3단계 최종 검증 후 4단계 CA/조회 adapter 개발을 진행한다.** Authority/Query service가 있으며 validity를 명시한 CA 생성은 settings 기본값 조회를 생략할 수 있다. 최초 설정 계약은 해소됐다. 4단계는 새 설치의 실제 최초 설정 API를 이용해 Leaf 발급/배포 URL과 setup 완료의 통합 흐름을 검증한다. fixture만 사용한 검증은 신규 설치 완료 증거와 구분한다.

CA/Leaf/인증서 HTTP adapter, 재발급·시리즈 수정/보관 service, 저장된 조회 metadata, 공개 CA 인증서/체인 조회와 runtime 주입을 작성했다. 현재 브랜치는 `codex/b06-stage4-implementation`이다. 최종 완료 판정은 아래 통합·독립 리뷰·네 DB 검증 gate 이후에 내린다.

## 2026-10-06 통합 및 독립 리뷰 진행

- HTTP 멱등성 충돌의 내부 코드 `idempotency_key_reused`를 문서의 공개 코드 `idempotency_conflict`로 매핑했다. 실제 RED 후 HTTP 전체 테스트 GREEN을 확인했다 (`26dd3c9`, `1f8c6c0`).
- 서비스·HTTP·SQL operations·porttest 회귀 테스트, artifact 검사와 `go vet ./...`가 통과했다. 이 결과는 전체 runtime 흐름 및 외부 DB 검증의 완료 증거가 아니다.
- Astra 독립 리뷰는 재발급 중 pending 전달 실패 종료의 폐기 누락, 미래 NotBefore 인증서의 유출 키 폐기 누락, commit-time 갱신 replay metadata 누락을 발견했다. Luna 작업 단위로 회귀 테스트와 수정 중이다.
- SQLite 실제 HTTPS 통합과 외부 세 DB의 검증은 진행 중이며 완료를 선언하지 않는다. 관리 화면은 이 단계의 API 범위와 구분하며, 기존 초기 화면을 전체 CA 관리 UI 완료로 표현하지 않는다.
- 실제 SQL 통합에서 전달 완료 후 키 custody가 계속 pending으로 남는 기존 gap을 확인했다. 갱신 전제 조건을 해소하도록 완료 전달의 계보를 확인하는 좁은 `MarkLeafKeyGenerationClientHeld` port와 동일 transaction의 전달 후처리를 보완한다. 일반 `SaveLeafKeyGeneration`의 renewal_count 저장 계약을 넓히거나 raw SQL fixture로 통합 문제를 가리지 않는다. 공개 수령 endpoint 구현은 여전히 5단계 범위다.

## 실행 순서와 소유권

루트가 계약·공유 interface·runtime·route 등록·통합·최종 보고를 소유한다. `jev-astra-luna-orchestrator`에 따라 Luna 실행 역할과 읽기 전용 Astra reviewer를 사용한다.

| 순서 | 담당 / 범위 | 결과와 수용 조건 |
| --- | --- | --- |
| 0 | 루트 + Luna tester: 3단계 HTTP 경계 회귀 검증 | 로그인 cookie, CSRF mode/origin, 비인증 거절, Settings If-Match/strict JSON, setup Root 조건, 역순 URL 게시를 검증. 기존 service 테스트만으로 HTTP 보장을 주장하지 않음 |
| 1A | Luna worker: 신규 CA HTTP adapter/DTO/테스트 | 목록·상세·Root/Intermediate 생성·이름·상태·키 파기·보관을 기존 OpenAPI에 연결. session/CSRF·scope·version·idempotency·오류 매핑 |
| 1B | Luna worker: Issuance service 신규 파일/테스트 | Reissue·UpdateSeries·ArchiveSeries 보완. 재발급 새 키, reason/transition 조건, 기존 기한/인증서 불변, version과 재시도·동시성 보장 |
| 2 | Luna worker: 신규 Leaf/Certificate HTTP adapter/DTO/테스트 | issue/renew/reissue/series update/archive 및 목록·상세. 재시도는 기존 결과 우선 확인, 토큰/개인키 없는 응답 |
| 3 | 루트: runtime 및 공유 route/interface | Authority/Issuance/Query와 crypto ports를 주입. 기존 origin/session/CSRF 경계 재사용, handler에 SQL/crypto 직접 호출 금지 |
| 4 | Luna tester + Astra reviewer | API/service/runtime 통합, 보안·동시성·공개 API 호환성 검토. 발견 사항 수정 후 관련 gate 재검증 |

1A/1B는 공통 파일을 동시에 수정하지 않는다. 기존 `issuance.go`, 공유 helper/contract/port 및 저장소 변경은 루트와 소유권을 합의한 뒤 실행한다. 2는 1B의 interface 확정 이후 시작한다. 관리 UI의 범위는 기존 4단계 API 수용 조건과 구분해 계획하고 HTML/HTMX도 동일 service를 호출한다.

## TDD와 검증 gate

`ecc:tdd-workflow`를 적용해 각 동작을 test target에 매핑하고 실제 RED 확인 뒤 최소 구현, 같은 target의 GREEN, 필요한 refactor 순서로 실행한다. 누락 method의 의도된 compile-time RED와 업무 동작의 runtime RED를 구분한다. 현재 branch의 RED/GREEN checkpoint commit과 증거 보고를 보존한다. 검증 명령은 저장소 지침의 허용된 Go test/vet와 artifact 검사에 대응시킨다.

- HTTP: 인증 없는 목록/상세 거절, Origin/CSRF 거절 시 service 미호출, path ID/body unknown 필드 검증, If-Match 428/412, idempotency 동일 재생/입력 불일치 409, DTO와 OpenAPI 일치.
- Service: Root/Intermediate 정책과 scope, 재발급 reason별 새 키·폐기 보완, series 수정/보관 불변조건, 최신 권한 재확인·동시 갱신 직렬화.
- 통합: 최초 settings 생성 API부터 Root → Intermediate → Leaf → renew/reissue를 실제 adapter로 실행. 기존 settings fixture 테스트는 별도 회귀 검증으로 유지한다.
- 최종: `python3 tools/check_artifacts.py`, `go test ./... -v`, `go vet ./...`, 상태 전이/동시성 race 검사. 변경 Go 파일 gofmt/goimports. 보안 변경 시 gosec 사용 가능 여부 기록. coverage를 측정하고 80% 목표 미달·skip·검증 공백을 사실대로 기록.
- SQLite와 PostgreSQL/MySQL/MariaDB의 관련 저장 경쟁 검증. DSN 없는 DB를 통과로 표시하지 않음. 새 검증 도구 의존성을 추가하지 않음.

## 준비 검증 증거

직전 동일 HEAD에서 전체 `go test ./... -v`, `go vet ./...`, `python3 tools/check_artifacts.py`가 통과했다. 외부 DB schema 3종은 DSN 부재로 skip됐다. HTTP/runtime는 테스트 파일이 없어 검증 공백이다. 준비 중 관련 race 검증 및 독립 리뷰 결과는 완료 후 아래에 기록한다.

- `go test -race ./internal/app/service ./internal/app/contract ./internal/adapter/http ./internal/runtime` 종료 코드 0. service/contract 통과, HTTP/runtime는 `[no test files]`로 실행 검증 공백 유지.
- Astra 읽기 전용 검토: 확인 범위에서 새 인증/CSRF 우회 결함을 발견하지 못했다. 최초 설정 경로 부재와 보안 HTTP 경계 테스트 부재를 중요 미완료 항목으로 확인했다. 명시적 validity를 사용한 Authority 생성 및 Query 연결의 분리 착수는 가능하다.
- `python3 tools/check_artifacts.py` 통과. 준비 문서만 추가했고 구현 코드·API·저장소 형식은 변경하지 않았다.
