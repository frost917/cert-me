# 인증서와 개인키 수명 정책

## 발급 프로필

- 기본 키는 ECDSA P-256. 선택지는 ECDSA P-384, RSA 2048/3072/4096. RSA를 선택한 CA의 기본 크기는 3072, Leaf는 2048이다. Ed25519 및 기타 알고리즘은 MVP 발급 범위 밖이다.
- 서버 TLS(serverAuth), 클라이언트 mTLS(clientAuth), 겸용(serverAuth + clientAuth) 프로필을 제공한다. 겸용은 명시적으로 선택해야 한다.
- 서버·겸용에는 DNS 또는 IP SAN이 하나 이상 필요하다. 클라이언트에는 식별 이름을 요구하고 DNS/IP/URI SAN을 선택적으로 허용한다. 이메일 SAN과 임의 확장 편집은 MVP에서 제외한다.
- 와일드카드는 DNS 이름의 맨 왼쪽 단일 레이블 `*.example.internal` 형태만 허용한다. URI는 절대 URI로 검증한다. 이름 정규화·중복 제거는 발급 전 수행한다.
- CA의 Basic Constraints와 keyCertSign/cRLSign, Leaf의 용도별 Key Usage/EKU를 서버에서 설정한다. 사용자가 CA 플래그를 임의 수정하지 못하게 한다. 서명에는 SHA-256 이상을 사용한다.
- 일련번호는 암호학적 난수로 생성한 양의 값으로 20옥텟 이하, 발급 CA 내 유일성을 DB에서 보장한다. 시간은 UTC로 저장한다.

## 유효기간과 계보

| 종류 | 기본 유효기간 |
| --- | --- |
| Root | 10년 |
| Intermediate | 5년 |
| Leaf | 1년 |

생성 시 관리자가 변경할 수 있다. Leaf 유효기간과 키 교체 주기는 인증서 관리 단위에 저장하며 갱신에 계승한다. 서비스 기본값 변경은 기존 관리 단위의 값을 덮어쓰지 않는다. 개별 교체 주기를 변경하면 아래 횟수 정책을 따른다. 하위 인증서 만료일은 발급 CA 만료일을 넘지 않는다. 초과 요청은 자동 축소하지 않고 가능한 기간을 안내한다. 가져온 인증서는 원본 만료일을 유지한다.

서버 생성 방식의 Leaf는 최초 발급 후 갱신 1·2회에는 기존 공개키를 사용하고 갱신 3회째 새 키를 생성한다. 키 교체 후 횟수를 초기화한다. 기본 교체 주기는 3회이며 관리자가 변경할 수 있다. 기간이 아닌 횟수 기준이다. 횟수 계산과 정책 변경은 아래 기준을 따른다.

기존 공개키로 발급 CA가 새 인증서를 서명할 수 있으므로 일반 갱신에 서버 보관 Leaf 개인키는 필요하지 않다. 클라이언트는 기존 개인키를 유지하고 인증서·체인만 교체한다. 갱신에는 관리자 인증과 관리 권한이 필요하며 공개 인증서 소지만으로 허용하지 않는다.

## 갱신 횟수 계산

| 상황 | 처리 |
| --- | --- |
| 최초 발급 | 현재 키 세대의 갱신 횟수 0 |
| 기존 키로 갱신 성공 | 새 인증서 저장 완료 시 1 증가 |
| 발급 실패 | 횟수 유지 |
| 공개 인증서 다운로드 실패 | 발급 완료 횟수는 유지하며 재다운로드로 추가 증가하지 않음 |
| 새 키로 교체 | 새 키 세대의 갱신 횟수 0 |
| 같은 요청 재시도 | 중복 발급 및 횟수 증가 방지 |
| 교체 주기 변경 | 다음 갱신부터 적용하며 누적 횟수 유지 |

다음 갱신의 순번(현재 횟수 + 1)이 설정한 교체 주기 이상이면 새 키로 발급한다. 예를 들어 기본 주기 3에서는 기존 키로 두 번 갱신하고 세 번째에 교체한다. 주기를 3에서 2로 줄였을 때 현재 횟수가 이미 2라면 다음 갱신에서 교체한다.

인증서 저장과 갱신 횟수·키 세대 변경은 원자적으로 처리한다. 아래 요청 ID 계약을 적용하고, 응답 손실 후 같은 요청을 재시도해도 별도 인증서로 중복 발급하지 않는다. 새 키의 개인키 수령 실패는 기존 수령 실패 정책에 따라 해당 인증서를 폐기하고 관리자가 다시 새 키로 발급한다.

가져온 Leaf는 등록 시 cert-me가 추적하는 갱신 횟수를 0으로 시작한다. 이는 기존 키가 새 키라는 의미가 아니며 화면에 '가져오기 이전 키 사용 이력은 포함하지 않음'을 표시한다. 관리자는 첫 재발급부터 새 키 사용을 선택할 수 있다. ACME에는 이 횟수 기반 정책을 적용하지 않는다.

## 개인키 보관

- CA 개인키는 서명을 위해 암호화해 보관한다. Root·Intermediate 모두 다운로드 기능 및 API를 제공하지 않는다.
- Leaf 개인키는 서버에서 생성해 수령 대기 중에만 암호화 보관한다. 일회성 수령 처리 후 서버 임시 사본을 삭제한다. 클라이언트 사본은 계속 사용한다.
- 예외: 대시보드에서 발급한 cert-me 자체 HTTPS 개인키는 내부 설치 후 별도 암호화 보관한다. 재시작 후에도 사용하며 일반 Leaf의 3시간 수령 기한·일회성 다운로드·수령 후 삭제 흐름을 적용하지 않는다.
- 저장 암호화 키는 운영자가 env 또는 file로 주입한다. 자동 생성하거나 DB에 보관하지 않는다.
- 암호화된 CA 개인키는 가져올 때 원본 암호로 복호화·검증하고 서버 저장 암호화로 재암호화한다. 원본 암호와 평문 개인키는 영속 저장하거나 로그에 남기지 않는다.
- 저장 암호화 키 교체는 내부 CLI의 rotate 명령에 기존·새 키를 함께 제공하여 백엔드에서 저장 개인키를 재암호화한다. 주입된 env·file은 변경하지 않는다. 외부 DB 복원 후에는 명시적 복구 모드에서 토큰·세션을 무효화하고 수령 대기 개인키를 삭제·해당 인증서를 폐기한다. 외부 백업 사본의 보존·삭제는 운영자 책임이다. 상세 범위는 [운영·보안 정책](./architecture.md)의 복구 정책을 따른다.

## 일회성 수령과 실패

대시보드와 curl은 동일한 수령 권한을 공유한다. 첫 유효한 GET 요청에서 권한을 원자적으로 소비하며 동시 요청 하나만 성공한다. 개인키 응답은 캐시하지 않는다. 개인키 수령 기한은 발급 후 기본 3시간이며 관리자가 변경할 수 있다. 기한 설정 변경은 새로 발급하는 개인키부터 적용하고 기존 수령 대기 건의 만료 시각은 유지한다. 기존 개인키의 수령 기한 연장은 제공하지 않는다. 대시보드에 수령 마감 시각과 남은 시간을 표시한다. 기한이 지나면 수령 요청을 거부하며 임시 개인키 삭제 및 인증서 폐기를 수행한다. 공개 인증서·체인의 반복 다운로드에는 이 수령 기한을 적용하지 않는다.

수령 실패 또는 만료 후 새 키·인증서 발급은 관리자가 명시적으로 실행한다. 서버는 실패를 감지하면 폐기 처리 및 재발급 필요 상태를 기록하며 자동으로 새 인증서를 반복 생성하지 않는다. 사용자가 저장 실패를 확인한 경우에도 관리자 재발급 작업을 제공한다.

재발급 권한은 전체 관리자, 해당 Leaf가 속한 Root CA 관리자, 해당 발급 Intermediate CA 관리자에게 부여한다. CA 범위별 관리자를 도입하면 이 범위 검사를 적용하며 다른 Root 또는 형제 Intermediate의 관리 권한만으로 재발급할 수 없다. MVP의 단일 전체 관리자 구성은 유지한다. CA 전환 시 원본과 대상 CA 양쪽의 관리 권한을 요구한다.

| 상황 | 처리 |
| --- | --- |
| 최초 발급 또는 키 교체 | 새 개인키·인증서 생성, 개인키 일회성 수령 |
| 일반 갱신 | 기존 공개키로 새 인증서 발급 |
| 개인키 수령 실패 | 해당 인증서 폐기, 관리자 실행으로 새 키·인증서 발급 |
| 수령 기한 만료 | 개인키 삭제 및 해당 인증서 폐기 |
| 개인키 유출 | 같은 키를 사용하는 유효 인증서 모두 폐기, 새 키·인증서 발급 |
| 공개 인증서 다운로드 실패 | 재다운로드 가능, 이 사유로 폐기하지 않음 |

서버는 클라이언트 저장 완료를 확실하게 알 수 없다. 감지 실패와 관리자 신고 실패 모두 아래 수령 실패 절차를 따른다. 정상 갱신은 교체 시간을 위해 기존 인증서를 즉시 폐기하지 않는다.

Leaf 공개 인증서·체인 다운로드 URL에는 일회성 토큰을 넣어 임시 링크로 제공한다. 링크는 한 번 사용하면 소비하지만 인증서 자체의 다운로드 횟수는 제한하지 않는다. 관리자는 필요할 때 새 링크를 생성할 수 있으며 공개 인증서 다운로드 실패는 새 링크로 재시도하고 인증서를 폐기하지 않는다. 공개 인증서 링크의 유효기간은 발급 후 기본 10분이며 관리자가 변경할 수 있다. 설정 변경은 새 링크부터 적용하고 기존 링크의 만료 시각은 유지한다. 같은 인증서의 새 공개 다운로드 링크를 발급하면 기존 미사용 공개 다운로드 링크를 무효화한다. CA 공개 인증서와 CRL의 접근 정책은 이 Leaf 링크 정책과 구분한다.

토큰 원문은 접근 로그·감사 로그에 남기지 않고 다운로드 응답의 캐시와 Referrer 전송을 방지한다. 유효한 GET 다운로드 요청을 처리할 때 토큰을 원자적으로 소비한다. HEAD 요청은 토큰을 소비하지 않고 파일도 반환하지 않는다. GET으로 접근하는 링크 미리보기 도구가 먼저 소비할 수 있으며, 이 경우 관리자가 새 링크를 생성한다. MVP는 별도 확인 화면 없이 curl로 바로 다운로드할 수 있게 한다. 공개 인증서 링크를 새로 만드는 작업이 개인키 재수령 권한을 복원해서는 안 된다.

주기적인 자동 발급·갱신은 장기 계획인 ACME로 제공한다. MVP의 관리자 수동 갱신은 유지한다. ACME는 클라이언트가 키를 보관하고 CSR을 제출하는 별도 흐름이며 서버 생성 키의 일회성 수령 절차를 강제하지 않는다. ACME의 키 생성·보관·교체 주기는 클라이언트 책임으로 한다. cert-me는 3회 갱신 키 교체 규칙을 ACME에 적용하지 않으며 클라이언트의 키 교체·설치 완료를 보장하지 않는다. 서버의 CSR 서명·발급 권한·알고리즘 등 발급 정책 검증 책임은 유지한다. 긴급 전환 시에도 ACME 클라이언트의 새 개인키 생성·설치는 클라이언트가 수행한다.

대시보드에서 PEM 개별 파일, ZIP 묶음, PKCS#12 형식을 선택한다. 개인키가 들어가는 형식은 최초 수령 때 선택하며, 수령 후 다른 형식으로 개인키를 다시 내보낼 수 없다.

## CA 공개 인증서 접근

- Root·Intermediate 공개 인증서 및 CA 체인은 인증 없이 고정 URL로 다운로드할 수 있다.
- CRL도 인증 없이 고정 URL로 제공한다. CRL URL은 갱신된 폐기 목록을 제공하는 용도이며 인증서 URL의 불변 정책과 구분한다.
- CA 목록·검색·관리 정보는 관리자 로그인이 필요하다.
- Root·Intermediate 개인키 다운로드는 제공하지 않는다.

공개 인증서 URL에는 이름 대신 변경되지 않는 CA 인증서 ID를 사용한다. CA 교체 후에도 이전 인증서 URL이 새 인증서를 반환하지 않는다. 체인도 해당 인증서와 연결된 경로를 식별하여 제공하며 자동으로 후속 CA 체인으로 바꾸지 않는다. 장기 교차 서명 지원 시 복수 경로의 식별 방식은 별도 설계한다.

대시보드에 CA 인증서의 SHA-256 지문을 표시한다. 인증서 다운로드와 장비의 신뢰 등록은 구분하며 최초 Root 신뢰 등록 시 지문을 확인할 수 있도록 안내한다.

## 정상 CA 교체

새 개인키로 후속 CA를 생성하고 기존 CA와 병행 운영하며 순차 전환한다. Leaf의 3회 갱신 키 교체 규칙은 CA에 적용하지 않는다.

- 기존 CA는 신규 발급 중지 상태로 전환한다. 기존 CA에서 갱신 인증서를 발급하는 것도 중지 대상이다.
- 기존 인증서를 정상 교체만을 이유로 즉시 폐기하지 않는다.
- 기존 CA는 남은 인증서의 폐기 처리와 CRL 발행을 유지한다. 신규 발급 중지를 CA 폐기나 개인키 삭제로 처리하지 않는다.
- Intermediate 교체는 같은 Root 아래 후속 Intermediate를 생성하고, 기존 Leaf를 갱신할 때 후속 Intermediate에서 발급하는 방식으로 진행한다.
- Leaf의 기존 공개키와 키 교체 횟수는 CA 전환만을 이유로 초기화하지 않는다. 클라이언트는 새 인증서와 발급 체인을 함께 배포한다.
- Root 교체는 새 Root 및 Intermediate 생성, 대상 장비에 새 Root 신뢰 추가, Leaf 순차 전환, 기존 계층 사용 종료 후 이전 Root 신뢰 제거 순서로 진행한다. MVP에서는 관리자가 전환을 진행하며 교차 서명은 후속 범위다.

발급 중지 상태와 인증서 자체의 유효·만료·폐기 상태는 구분한다. 종료·보관·키 파기는 아래 CA 종료 정책을 따른다.

## CA 키 유출 시 긴급 처리

정상 교체와 구분되는 긴급 전환으로 관리한다. 영향받은 계층의 신규 발급·갱신을 중지하고 대시보드에 영향받는 인증서 목록과 전환 상태를 제공한다.

- Intermediate 키 유출: 부모 Root에서 해당 Intermediate 인증서를 폐기하고 Root CRL을 갱신한다. 새 키의 후속 Intermediate를 마련하고 하위 인증서를 새 CA에서 재발급·배포한다.
- Root 키 유출: 해당 신뢰 계층 전체를 새 Root 및 Intermediate로 교체하고 하위 인증서를 전환한다. 대상 장비에서 기존 Root 신뢰를 제거해야 한다. 서비스 내부 상태 변경이나 CRL 발행만으로 신뢰 제거가 완료됐다고 표시하지 않는다.
- 하위 인증서에는 CA 유출로 인한 영향 상태를 기록한다. 상위 CA 폐기와 하위 인증서 각각의 명시적 폐기 기록은 구분한다. 영향 표시만으로 하위 인증서의 CRL 등록이 완료됐다고 간주하지 않는다.
- 인증서 재발급 완료와 대상 장비의 배포·신뢰 제거 완료를 구분한다. MVP에서 외부 장비의 전환이 자동으로 완료됐다고 추정하지 않는다.
- 유출 신고 계정·시각·대상 CA, 발급 중지, 폐기 및 전환 작업은 감사 기록으로 남긴다.

긴급 전환에서는 영향을 받은 Leaf를 새 CA에서 재발급할 때 갱신 횟수와 관계없이 새 개인키를 생성한다. 기존 공개키는 재사용하지 않는다. 새 키 세대로 전환하고 갱신 횟수를 초기화한다. 새 개인키는 일반 발급과 동일하게 일회성으로 수령하며, 수령 실패 시 해당 새 인증서를 폐기하고 다시 새 키·인증서를 발급한다. 클라이언트는 개인키·인증서·체인을 함께 교체한다.

## CA 종료와 보관

- 한 번 발급에 사용한 CA 및 발급 완료 인증서는 일반 삭제하지 않고 보관 상태로 남긴다. 공개 인증서·계보·폐기 데이터는 감사 로그 정리와 무관하게 유지한다.
- 정상 전환 완료는 관리자가 장비 전환을 확인해 표시한다. 등록된 하위 인증서 모두가 만료될 때까지 기존 CA의 CRL을 주기적으로 발행한다. 최종 CRL은 마지막 하위 만료일까지 검증에 사용 가능하도록 미리 발행한다. CA 만료 후 유효한 CRL을 계속 서명할 수 있다고 가정하지 않는다.
- 발행 종료 후 마지막 CRL과 공개 인증서는 계속 제공하되 만료 CRL을 현재 유효하다고 표시하지 않는다. CA 키는 자동 파기하지 않는다. 하위 인증서 만료·필요한 CRL 발행 완료·발급 중지 조건을 만족하면 전체 관리자가 명시적으로 파기할 수 있다. 관련 기록은 보존한다.
- Intermediate 유출은 부모에서 caCompromise 사유로 폐기한다. 하위 Leaf는 'CA 유출 영향'으로 표시하며 자동으로 개별 CRL 항목을 추가하지 않는다. 명시적 개별 폐기는 지원한다. Root 유출은 하위 계층 발급을 모두 차단한다.
- 긴급 전환은 새 CA·새 Leaf 키로 수행한다. 외부 배포와 신뢰 제거는 관리자가 대상별 완료 표시한다. 자동 검증 완료라고 추정하지 않는다. 유출된 CA 키의 즉시 파기는 제공하지 않고 우선 사용 중지한다.

## CRL

CRL 설정 범위는 주기 5분~24시간, 유효기간은 주기의 최소 2배~7일이다. 최종 CRL도 이 범위 안에서 CA 만료 전에 발행하고 등록된 마지막 하위 인증서 만료일까지 포함하도록 일정을 잡는다. 이 조건을 충족하지 못하면 종료 완료로 표시하지 않는다.

Root는 자신이 발급한 Intermediate, Intermediate는 자신이 발급한 Leaf의 폐기 정보를 발행한다. 폐기 시 즉시 갱신하고 폐기 내역이 없어도 주기적으로 재발행한다. 인증 없이 접근 가능한 고정 배포 URL을 제공한다.

| 항목 | 확정 정책 |
| --- | --- |
| 정기 재발행 | 기본 12시간마다 |
| 유효기간 | 발행 시점부터 기본 48시간 |
| 폐기 발생 | 즉시 재발행 |
| 재시작 | CRL 상태 확인 후 재발행 시점이 지났으면 갱신 |
| 설정 | 관리자가 재발행 주기와 유효기간 변경 가능 |

CRL 번호는 CA별로 단조 증가시키고, 기존 발행 번호 및 가져온 CRL 번호보다 큰 번호로 새 CRL을 발행한다. 번호 예약은 CA별 트랜잭션으로 처리하며 실패한 번호는 재사용하지 않는다. 게시 시 현재 게시 번호보다 큰 경우만 원자적으로 교체해 늦게 끝난 작업이 최신 CRL을 덮어쓰지 못하게 한다. 폐기 데이터 변경 세대도 기록하여 생성 중 추가된 폐기는 후속 작업으로 반드시 게시한다. 복원 시 최신 외부 CRL 또는 운영자 제공 최대 번호를 확인한다. 클라이언트가 캐시된 CRL을 사용하면 즉시 재발행해도 접속 차단이 늦어질 수 있다.

폐기는 키 자체가 아닌 인증서에 적용한다. 실제 접속 차단 시점은 클라이언트의 폐기 검사 및 캐시 정책에 좌우된다. CA 키 유출 시 기본 처리 흐름은 위 긴급 처리 정책을 따르며 하위 인증서의 자동 개별 폐기는 하지 않으며 명시적 개별 폐기를 지원한다.

## 수령 처리와 요청 재시도 계약

- 개인키의 유효한 GET에서 토큰 소비와 DB 임시 암호문 삭제를 커밋한 뒤 메모리의 묶음을 전송한다. HEAD·Range·조건부 요청은 개인키를 반환하거나 토큰을 소비하지 않고 거부한다. 재다운로드·전송 재개는 지원하지 않는다.
- 전송 중 상태를 영속화한다. private 전송 후처리 기록에 실패하거나 commit이 불명확하면 일반 요청을 닫고 프로세스를 종료하여 재시작 복구를 강제한다. 감지된 실패 또는 재시작 후 남은 전송 중 상태는 보수적으로 수령 실패 처리해 인증서를 폐기한다. 사용자는 관리자 화면에서 저장 실패를 신고하고 폐기 후 새 키로 재발급할 수 있다. 서버가 저장 완료를 보증한다고 표시하지 않는다.
- 발급·갱신·재발급에는 요청 ID를 사용한다. 계정·작업·요청 ID별 결과를 보존하며 같은 ID와 다른 입력은 충돌로 거부한다. UI가 재시도할 때 같은 ID를 유지한다. 중복 방지가 개인키 재수령으로 이어져서는 안 된다.
- 기한 만료 정리는 매분 실행하고 요청 시에도 만료를 검사한다. CRL 발행 실패 시 폐기 상태는 유지하고 발행 작업을 재시도한다. 성공 전에는 'CRL 반영 대기/실패'를 표시한다.

수령 상태는 대기 → 전송 중 → 전송 완료 또는 실패로 관리한다. 전송 완료는 서버의 응답 쓰기 완료만 뜻한다. 대기·전송 중·실패·기한 만료 상태의 키로 일반 갱신하지 못하게 한다. 실패·만료 후에는 관리자 실행으로 새 키를 발급한다. 인증서 계보와 키 세대를 별도로 보관하고 동일 계보의 동시 갱신을 직렬화해 분기나 횟수 손실을 방지한다. 폐기되었거나 유출 영향이 있는 인증서의 기존 키를 일반 갱신 경로로 재사용하지 않는다.

다운로드 토큰은 암호학적 난수로 생성하여 해시만 저장하고 인증서·수령 권한·용도·만료 시각에 결합한다. 공개 링크와 개인키 수령 토큰은 서로 대체할 수 없다. 개인키 링크를 분실하면 관리자가 동일 수령 권한의 토큰만 교체할 수 있다. 이전 토큰을 무효화하며 원래 기한을 유지하고, 이미 소비된 권한은 복원하지 않는다. 토큰 재출력은 하지 않는다.

PEM/ZIP/PKCS#12 중 선택한 개인키 응답 묶음은 소비 커밋 전에 메모리에서 완성한다. 변환 실패는 토큰을 소비하지 않는다. PKCS#12 암호는 해당 수령 요청의 전용 헤더로 전달하고 저장·로그하지 않는다. URL에는 넣지 않으며 대시보드와 curl 모두 이 방식을 지원한다. 서버 임시 파일에 평문 키나 묶음을 남기지 않는다. 개인키 응답과 토큰 화면에는 Cache-Control: no-store와 Referrer-Policy: no-referrer를 적용한다.


일회성 삭제는 현재 운영 DB의 임시 암호문과 애플리케이션 참조를 제거한다는 의미다. DB WAL·스토리지·백업까지 물리적으로 안전 삭제했다고 보장하지 않는다. 외부 사본은 운영자의 보존 정책을 따른다.
