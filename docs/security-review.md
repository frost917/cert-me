# 설계 보안 검토 — 2026-09-09

## 범위와 방법

사용자 요청에 따라 gpt-5.6-luna, reasoning effort=max 에이전트 3명이 인증·권한, PKI·키 관리, 저장소·운영을 독립 검토하고 총괄 에이전트가 문서 간 근거를 대조했다. 검토 대상은 docs의 현재 설계, OpenAPI 계약, 초기 SQL 및 관련 생성기다. 운영 백엔드에 대한 침투 테스트나 구현 안전성 인증은 아니다. 외부 의존성의 최신 취약점 전수 조사도 범위에 포함하지 않는다.

심각도는 해당 공백이 그대로 구현될 경우의 영향을 기준으로 한다. 확정된 사용자 정책의 잔여 위험, 구체적인 설계 공백, 선택적 방어 강화를 구분한다. 권고는 검토 결과이며 기존 제품 정책을 자동으로 변경하지 않는다.

## 검토 결과

현재 설계만으로 실제 악용 가능한 구현 취약점을 확정할 수는 없다. 일회성 소비·비밀 목적 분리·세션 폐기·CRL 게시의 핵심 보호 규칙은 존재한다. 다만 아래 설계 공백은 구현 전에 보완해야 한다. 높은 심각도는 명시한 전제가 성립할 때의 영향이며, 모든 배포에서 이미 노출된다는 뜻이 아니다.

### SEC-01 — URL 토큰을 처리하는 프록시·관측 도구의 비밀 경계

**분류: 조건부 높은 위험 / 배포 계약 공백.**

근거: `api-contract.md:113–125`, `architecture.md:54–56`은 개인키 수령과 비밀번호 재설정에 URL bearer 토큰을 사용한다. `api-contract.md:15`는 애플리케이션 로그에서 원문 경로를 제외하지만 프록시·APM·추적 도구의 수집 규칙까지 정의하지 않는다.

미소비 토큰이 프록시 access log나 추적 시스템에 기록되면 해당 로그 접근자가 개인키를 먼저 수령하거나 관리자 비밀번호를 재설정할 수 있다. 응답의 no-store/no-referrer는 이미 요청을 받은 프록시의 로깅을 막지 않는다. 재설정 화면 GET은 토큰을 소비하지 않으므로 화면을 연 뒤에도 이 위험이 남는다.

권고: 기존 URL 방식과 3시간 정책은 유지하되, 배포 예제에 `/download/*`, `/reset-password/*`의 원문 경로·query·Referer 마스킹을 포함한다. 오류 로그·APM span·프록시 임시 파일/응답 캐시도 확인한다. 재설정 화면은 토큰을 메모리로 옮긴 뒤 history.replaceState로 주소 표시/현재 방문 기록에서 제거하고 제3자 자산을 사용하지 않는다. 이는 이미 남은 외부 로그를 지우는 조치가 아님을 명확히 한다.

검증: 알려진 테스트 토큰으로 성공·실패·잘못된 경로 요청을 보낸 뒤 앱/프록시/추적 출력에 원문이 없는지 확인한다. 링크를 연 것만으로 재설정 권한이 소비되지 않는 기존 동작도 유지한다.

### SEC-02 — 암호화 PKCS#8의 연산량 상한

**분류: 중간 / 설계 공백.**

근거: `pki-import.md:59`, `dependencies.md:13`, `backend-implementation.md:208–212`는 알고리즘 allowlist와 semaphore를 정하지만 PBKDF2 반복 횟수 상한은 정하지 않는다. 로컬에 설치된 고정 버전 youmark/pkcs8의 `kdf_pbkdf2.go`, `DeriveKey`도 입력 IterationCount를 그대로 pbkdf2.Key에 전달한다.

관리자가 외부에서 받은 작은 암호화 키 파일을 import할 때 과도한 반복 횟수로 CPU를 오래 점유할 수 있다. 인증이 필요한 경로이므로 무인증 원격 공격으로 단정하지 않는다. 동시 실행 수 제한은 작업 하나의 비용을 제한하지 않으며 context timeout만으로 라이브러리 내부 계산이 종료된다고 보장할 수 없다.

권고: 복호화 호출 전에 ASN.1 파라미터를 파싱하고 반복 횟수·salt 길이·파생 키 길이·암호문 길이와 묶음 전체 작업량의 상한을 검증한다. 지원 서버에서 측정한 예산을 기준으로 상한을 고정하고 초과 입력은 명시적으로 거부한다. 로그인 Argon2id도 비밀번호 해시 실행 전 admission limit과 프로세스 전체 메모리/동시 실행 예산을 둔다.

검증: 작은 파일에 매우 큰 반복 횟수를 넣어 실제 KDF 호출 전에 거부되는지 확인한다. 여러 파일의 합산 비용과 동시 로그인 상황에서도 CRL 작업의 진행을 확인한다.

### SEC-03 — import 공개 메타데이터의 저장 허용 필드

**분류: 중간 / 기계 계약의 구체성 부족.**

근거: OpenAPI의 TakeoverInput.evidence, ImportPreview.manifest, ImportMetadata.preview_manifest는 자유 속성을 허용한다. `data-model.md:117–118`은 evidence_json/input_manifest_json/result_json을 저장하면서 공개 자료만 보존하도록 요구한다.

문서는 이미 비밀 저장을 금지하므로 실제 비밀 저장이 확정됐다고 볼 수 없다. 그러나 입력 메타데이터를 그대로 저장하는 구현과 서버가 공개 필드만 재구성하는 구현을 스키마만으로 구분하기 어렵다. 특히 import 입력에는 합법적으로 해제 암호가 포함되어 잘못된 전체 객체 복사가 민감정보의 영속화로 이어질 수 있다.

권고: 버전별 manifest/evidence DTO의 허용 필드를 명시하고 입력 DTO와 저장 DTO를 분리한다. 서버가 파일 지문·공개 ID·검증 결과로 저장 manifest를 재구성한다. 알 수 없는 필드와 과도한 깊이를 거부하며 단순히 password 같은 필드명만 지우는 방식에 의존하지 않는다. 자유 텍스트에 임의로 적힌 모든 비밀을 자동 식별할 수 있다고 주장하지 않는다.

검증: passphrase와 알 수 없는 중첩 필드를 포함한 요청에 대해 DB·결과 조회·감사 기록에 입력 객체 전체가 복사되지 않는지 확인한다.

### SEC-04 — 프록시 IP 추출 알고리즘

**분류: 중간 / 설계 공백.**

근거: `architecture.md:72`는 신뢰 프록시의 IP 헤더만 수용하고 `architecture.md:154`는 계정/IP별 시도 제한을 요구한다. 허용 CIDR·복수 hop 처리·충돌 헤더 처리 방식은 정하지 않았다.

허용 프록시를 통해 들어왔다는 이유만으로 X-Forwarded-For의 첫 값을 사용하면, 외부 클라이언트가 추가한 주소가 rate limit과 감사 IP로 선택될 수 있다. 이는 모든 신뢰 프록시 구성에서 생기는 문제가 아니라 파싱/덮어쓰기 규칙을 잘못 구현한 경우의 위험이다.

권고: 기본은 RemoteAddr이며 명시적 신뢰 CIDR에서 온 연결만 전달 헤더를 처리한다. 지원 헤더를 하나로 정하고 체인을 신뢰 경계에서 역방향으로 검사해 첫 비신뢰 hop을 선택한다. 잘못된/충돌하는 헤더와 IPv6 정규화를 명시한다. Origin 비교는 설정된 출처를 사용하며 Forwarded-Host/Proto로 임의 변경하지 않는다. 초기 설정 이전 출처 결정도 별도로 고정한다.

검증: 직접 접속의 위조 헤더, 신뢰 프록시 뒤에 추가된 위조 주소, 복수 hop, IPv6를 테스트한다.

### SEC-05 — HTML·HTMX의 브라우저 방어 계약

**분류: 중간 / 방어 강화 명세 공백.**

근거: `architecture.md:21`은 html/template+HTMX를 사용하며 `api-contract.md:12–15`는 세션/CSRF/cache를 정한다. CSP·frame-ancestors·HTMX의 동적 실행 정책은 별도로 정하지 않았다.

html/template 채택 자체는 보호 수단이며 XSS가 확인된 것은 아니다. 다만 인증서 이름·Subject·import 오류 같은 외부 문자열을 HTML로 승격하거나 HTML 속성에 잘못 넣는 향후 변경의 영향이 크다. frame 차단 정책도 명시할 필요가 있다.

권고: 신뢰되지 않은 값의 template.HTML 등 안전 타입 변환을 금지하고 문맥에 맞게 escape한다. 로컬 자산 기준 CSP, frame-ancestors 'none', nosniff를 명시하고 HTMX eval/스크립트 실행 의존을 검토한다. 부트스트랩/만료 복구와 충돌할 수 있는 HSTS preload/includeSubDomains를 무조건 기본값으로 강제하지 않는다.

검증: Subject·이름·오류 문자열의 HTML 주입, iframe 임베딩, HTMX 조각 렌더링을 실제 브라우저에서 확인한다.

### SEC-06 — 실행 중 개인키 전송 후처리 실패의 회수 경로

**분류: 조건부 높음 / 복구 설계 공백. 최우선 보완.**

근거: `backend-implementation.md:239–240`은 최대 5초 후처리 실패 시 transferring을 남기며, `backend-implementation.md:275`는 재시작 복구를 정의한다. `storage-migrations.md:48`은 writer 연결 상실 시 프로세스를 종료하므로 그 경우는 이미 재시작 복구로 이어진다.

남는 경우는 연결이 유지되는 일시적 트랜잭션 오류·writer 대기/후처리 timeout 등이다. 개인키 전달이 실패했거나 결과가 불명확한데 후처리 저장만 실패하고 프로세스가 계속 실행되면, 폐기·CRL 작업 없이 transferring이 잔류할 수 있다. 현재 문서에는 이를 살아 있는 프로세스에서 언제 회수하는지 명시되지 않았다. 성공 전송 기록만 실패한 경우까지 실제 키 유출로 단정하지는 않는다.

권고: 소비 단계에 전송 attempt 식별자와 회수 기준을 결합하고 실행 중 후처리 재시도/회수 경로를 정의한다. 활성 전송과 이미 종료된 미확정 전송을 구분하며, 실제 Send 중인 요청을 단순 수령 기한 초과만으로 회수하지 않는다. 전송의 최대 실행 시간과 취소·종료 확인을 정한 뒤, 회수 시 failed·폐기·CRL 작업·감사를 같은 트랜잭션으로 기록한다. 안전한 실행 중 회수를 구현하지 않는다면 후처리 미확정 시 서비스 종료 및 기존 시작 복구를 강제하는 대안도 가능하다.

검증: 소비 성공 → Send 실패/성공 → 후처리 timeout → DB 정상화의 네 가지 조합을 주입한다. 재시작 없이 회수되거나 명시적으로 서비스가 종료되는지, 늦은 성공 callback이 failed를 되돌리지 않는지, 활성 전송과 회수가 경쟁하지 않는지 확인한다.

다음은 팀에서 지적했으나 총괄 대조 결과 새 구현 결함으로 집계하지 않았다. 정책을 변경하지 않는 범위의 운영 전제와 한계를 명시한다.

## 상호 검토에서 제외·조정한 후보

- **OpenAPI의 security: []만으로 CSRF 우회라고 할 수 없다.** 로그인/최초 계정/재설정은 원래 비로그인 경로이며 필수 CSRF 헤더와 문서상의 nonce 결합·Origin 검증이 존재한다. nonce 쿠키 속성/출처 규칙을 더 구체화하고 통합 테스트해야 하지만 현재 정책이 CSRF를 생략한 것은 아니다.
- **자유 JSON을 곧 비밀 저장 취약점으로 단정하지 않았다.** 공개 필드만 저장한다는 명시 규칙이 있으므로 SEC-03은 입력→저장 변환의 명세 공백으로 분류했다.
- **교차 행 무결성을 전부 SQL FK가 보장하지 않는 것은 명시된 선택이다.** `storage-migrations.md:94` 및 관련 서비스 규칙을 따른다. revocation의 certificate ID/issuer/serial, delivery의 certificate/key generation 불일치를 모든 저장 어댑터 경로에서 거부하는 검증은 필요하다. 복합 FK는 추가 방어 대안이다.
- **감사는 침해된 DB 운영자로부터 변조 불가능하다고 정의되지 않았다.** 감사 보존 기간에 따른 정리가 필요하다. 외부 불변 감사 저장소는 선택적 강화이며 단순 hash chain만으로 전체 재작성/삭제까지 막는다고 주장하지 않는다.
- **CA 공개키/개인키 다운로드 금지, 목적별 암호문, 재설정 즉시 세션 폐기, 소비 commit 이전 전송 금지, CRL generation/번호 단조성은 문서에 존재한다.** 빠진 통제로 재집계하지 않았다. 실제 준수는 구현 후 검증해야 한다.

## 처리 결정 — 2026-09-09

후속 사용자 지시에 따라 기존 정책 안의 SEC-01~06 보완을 확정했다. 앞 절의 권고와 줄번호는 감사 당시 기록이다. 현재 구현 계약은 아래 담당 문서를 따른다. **상태는 설계 반영 완료이며 운영 구현 검증은 미완료다.**

| 항목 | 확정한 조치 | 담당 문서 |
| --- | --- | --- |
| SEC-01 | 프록시/관측 경로 마스킹·캐시/디스크 버퍼 금지, reset 토큰 메모리 보관 및 URL 제거 | [운영](./architecture.md), [HTTP](./api-contract.md) |
| SEC-02 | PKCS#8 반복 상한 200만/묶음 400만, 파라미터 사전 검증, Argon2id 고정 프로필과 실행 수 제한 | [import](./pki-import.md), [운영](./architecture.md) |
| SEC-03 | ImportManifest/TakeoverEvidence v1 폐쇄 스키마와 공개 저장 DTO 재구성 | [API](./api-contract.md), [데이터](./data-model.md), [OpenAPI](../api/openapi.json) |

초기 Docker 예제는 loopback 호스트 바인딩과 공개 지문 확인을 안내한다. 계정 생성에 새 토큰이나 실제 호스트 SAN 입력을 요구하지 않는다. SQL은 기존 JSON 컬럼·transferring 상태로 충분하므로 변경하지 않는다.

현재 사용자 답변을 기다리는 필수 항목은 없다. 온라인 Root를 오프라인/HSM으로 분리하기, 최초 가입 승인 절차 추가, 외부 rollback 감지 상태 운영, 변조 방지 외부 감사 저장소 도입은 운영 모델 변경이므로 이번에 도입하지 않는다. 필요해질 때 별도로 논의하며 기존 합의는 유지한다.
