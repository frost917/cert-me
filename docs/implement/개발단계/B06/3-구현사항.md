# 3단계 구현사항 — 인증·설정·초기 화면

기준일: 2026-10-05 · 브랜치: `codex/b06-stage3-completion` · 상태: **3단계 기능 구현·자동 검증 완료, 4단계 착수 가능**

## 구현된 기능

- 사용자 승인에 따라 `POST /api/v1/setup/settings`를 추가했다. 관리자 세션+CSRF, `pki_required`·설정 없음 조건에서 전체 설정을 명시 입력해 version 1로 생성한다. 설정·감사를 한 트랜잭션에 저장하며 기존 설정은 덮어쓰지 않는다. 이후 GET/PATCH·If-Match 계약은 유지한다.
- 최초 설정이 없을 때 화면에서 전체 설정을 입력할 수 있다. 응답 손실·본문 읽기 중단·경쟁 생성의 409는 GET으로 저장된 설정과 version을 확인한 뒤 일반 PATCH를 사용한다. 요청 Host나 임의 URL 기본값은 사용하지 않는다.
- URLValidator의 호스트 문법을 Origin 검사와 맞춰, 저장 후 CSRF 요청이 불가능해지는 잘못된 DNS/모호한 숫자 주소를 저장 전에 거부한다. DNS 조회나 외부 fetch는 하지 않는다.
- setup 완료는 본문 없는 요청 또는 `{}`를 허용하고 그 외 JSON 내용은 서비스 호출 전에 거부한다. OpenAPI의 해당 Empty 본문은 선택적이다.

- `GET /api/v1/auth/csrf`가 유효 세션의 CSRF를 재발급하거나 pre-auth CSRF를 발급한다. `mode=preauth`는 유효 세션이 있어도 비로그인 흐름을 선택하고, `mode=session`은 세션을 요구한다.
- 로그인은 `__Host-certme_session` Secure·HttpOnly·SameSite=Strict·Path=/ 쿠키를 발급하고, 첫 관리자 생성은 기존대로 자동 로그인하지 않는다. 로그아웃은 세션을 삭제하고 쿠키를 제거한다. `/auth/me`는 현재 계정과 만료 시각을 반환한다.
- `/auth/password-reset`은 reset token과 새 비밀번호를 `secret.Input`으로 전달한다. 재설정 화면은 token을 서버 렌더링 값에 넣지 않고 브라우저 메모리에 옮긴 뒤 `history.replaceState`로 URL을 `/`로 교체한다. 재설정 화면은 세션이 있어도 pre-auth CSRF를 요청한다.
- 로그인/재설정 rate limit은 429와 `Retry-After`를 반환한다. Retry-After 계산용 내부 절대시각 필드는 JSON 오류 응답에서 제외한다. reset_pending/disabled 계정의 로그인 거절도 일반 `invalid_credentials`로 합친다.
- 인증된 `/settings` GET/PATCH와 `/setup/complete`를 연결했다. 설정 변경은 If-Match/ETag를 적용한다. 설치 완료는 저장된 설정 snapshot과 Root authority가 최소 하나 있는지 확인한다.
- Setup 상태의 임시 HTTPS 표시는 installation TLS version의 `source`를 읽어 bootstrap 여부를 판단한다. URL 검증은 Origin 정규화가 거부하는 명시적 빈 포트도 저장 전에 거부한다.
- 초기 관리자·로그인·설정·재설정 화면을 로컬 `html/template`, CSS, JavaScript, 고정 버전 HTMX 2.0.10으로 추가했다. HTMX eval/script-tag 실행과 indicator CSS 자동 삽입을 끄고 동일 출처 자산만 사용한다.
- 설정 URL 변경이 성공하면 handler가 `{settings version, URL}` 불변 snapshot을 CAS로 원자 게시한다. 응답이 역순으로 도착해도 낮은 version이 더 높은 version을 되돌리지 않는다. 이전 pre-auth 토큰은 변경된 origin에서 검증되지 않는다.

## 사용 모듈과 실제 타입

- `internal/adapter/http/setup.go`: `SetupApplication`, `IdentityApplication`, `SettingsApplication`, `SetupHandlerConfig`, `setupHandler`, `NewSetupHandler`.
- `internal/adapter/http/identity.go`: `getCSRF`, `postLogin`, `postLogout`, `getSession`, `postCompleteReset`, 세션 cookie·요청 metadata·strict JSON helper와 응답 DTO.
- `internal/adapter/http/settings.go`: `getSettings`, `patchSettings`, `postCompleteSetup`, `expectedVersion`, settings 응답 DTO.
- `internal/adapter/http/pages.go`와 `internal/adapter/http/web/`: `registerWebRoutes`, embedded template/static assets, `index.html`, setup status fragment, `app.js`, `app.css`, HTMX license.
- `internal/app/contract`: `IdentityAuthenticateCommand`의 선택적 `CSRFToken`, `Principal`의 private CSRF proof, 기존 Login/Logout/Authenticate/CompleteReset/IssueCSRF·Settings·Setup command/view 타입.
- `internal/app/service`: 기존 `IdentityService`, `SettingsService`, `SetupService`. `IdentityService.Authenticate`가 요청 CSRF hash를 확인해 Principal에 담고 `requireCurrentAuth`가 실제 mutation transaction 안에서 회전을 재확인한다. `SetupService.Complete`가 `installationHasRoot`를 호출한다.
- `internal/runtime/runtime.go`: `prepareServices`가 Setup·Identity·Settings 서비스를 만들고 HTTP adapter에 주입한다. Settings URL 검증은 기존 `cryptoformats.URLValidator`를 사용한다.
- `internal/adapter/http/web/htmx.min.js`: `dependencies.lock.json`의 npm tarball SHA-512와 일치하는 htmx.org 2.0.10 배포 파일.
- `tools/generate_openapi.py`: CSRF 조회 `mode` query 계약을 생성하고, `api/openapi.json`은 생성기로 다시 만들었다.

## 의도한 결합

```text
runtime.prepareServices
  → SetupService / IdentityService / SettingsService
  → NewSetupHandler
      → HTTP handler가 strict 입력·Origin·cookie·CSRF 경계를 처리
      → typed contract를 service에 전달
      → 응답 DTO/template만 렌더링
```

HTTP handler는 DB·SQL·crypto engine을 직접 호출하지 않는다. 세션 Principal은 IdentityService가 만들고, mutation handler는 CSRF token을 Authenticate에 넘긴다. 서비스의 기존 `requireCurrentAuth`가 세션과 CSRF proof를 같은 변경 transaction에서 재검사한다. HTML은 고정 template과 local assets만 사용한다.

## 미완료·제약

- 설정이 없을 때 GET/PATCH는 기존대로 `settings_not_configured`를 반환하며, 승인된 최초 생성 API/화면으로 생성한 뒤 수정한다. 이전의 PR 질문 보류 항목은 사용자 승인으로 해소됐다.
- CA/인증서 관리 대시보드는 4단계 이후다. 설치 완료 API는 Root가 없으면 거부하지만 Root 생성/가져오기 화면과 API는 아직 연결하지 않았다.
- HTTP 경계 및 SQLite/PostgreSQL/MySQL/MariaDB runtime의 실제 HTTPS/SQL 흐름과 race 검사를 수행했다. 실제 브라우저 도구는 unavailable이며 UI는 실제 app.js의 DOM/fetch 단위 테스트로 확인했다. 전체 2단계 운영 장애 검증과 4단계 Root API를 포함하는 신규 설치 E2E는 별도다.

## 검증 상태

현재 작업의 RED/GREEN 커밋·실제 명령·커버리지·검증 공백은 [3단계 TDD 증거](./3-TDD-검증.md)를 따른다. 아래는 이전 구현 시점의 기록이다.

- 변경 Go 파일 `gofmt` 완료.
- `GOCACHE=/tmp/cert-me-go-build-cache go build ./...` 통과.
- `GOCACHE=/tmp/cert-me-go-build-cache go vet ./...` 통과.
- `GOCACHE=/tmp/cert-me-go-build-cache go test ./... -v` 통과. Postgres/MySQL/MariaDB schema subtest는 전용 DSN이 없어 skip됐고 SQLite 검사는 통과했다. `TestComplete_RequiresRootAuthority`를 추가하고 성공 경로 fixture에 Root를 준비하도록 보정했다.
- `python3 tools/check_artifacts.py` 통과 (SQL checksum, OpenAPI 재생성, 문서 링크).
- `python3 -m json.tool api/openapi.json` 통과.
- Astra의 읽기 전용 보안 재검토에서 설정 URL의 오래된 값 재게시 결함을 발견했고 versioned atomic snapshot/CAS로 수정했다. 후속 재검토는 해당 게시 경로에 blocker가 없다고 확인했다. 이후 `gpt-6.1-sol` 코드 검토에서 네 개 P2 응답/검증 결함이 추가로 발견되어 수정했다. 이 네 수정의 후속 독립 검토와 실제 동시 실행 검증은 아직 하지 않았다.
