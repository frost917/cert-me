# B06 구현 예정 단계

기준일: 2026-09-30 · 작업 브랜치: `codex/b06-implementation`
현재 진행 단계: **3단계 — 인증·설정·초기 화면 (부분 구현)**

B06의 전체 수용 조건은 [백엔드 구현 설계 §11](../../../backend-implementation.md)과 [개발 순서와 검증](../../../planning.md)을 따른다. 이 문서는 **구현 예정 단계**를 관리한다. 실제 코드가 작성된 단계만 `n-구현사항.md`에 구현 기능·실제 Go 타입·모듈·결합을 기록한다. 현재 구현 기록은 [1단계](./1-구현사항.md), [2단계](./2-구현사항.md)다.

## 2026-10-05 · 4단계 진입 검증

**판정: 4단계 코드 작업은 시작 가능. 새 설치의 settings 초기화부터 Leaf 발급까지를 완료 기준으로 검증하는 것은 보류.**

- `python3 tools/check_artifacts.py`, `go test ./... -v`, `go vet ./...`가 통과했다. SQLite schema 검사는 통과했고, PostgreSQL·MySQL·MariaDB schema 검사는 전용 DSN이 없어 skip됐다. HTTP adapter에는 아직 handler 테스트가 없다.
- Authority/Query 서비스는 존재해 목록·상세·Root 생성·이름/상태/보관 API 연결을 시작할 수 있다. Authority 생성은 validity를 명시하면 service 설정 기본값 조회를 생략할 수 있다.
- Leaf 발급·갱신은 service_url과 전달/유효기간 기본값이 포함된 settings 행을 요구한다. 초기 `service_url` 입력 경로를 정하지 않은 상태라 신규 설치의 Leaf 흐름, `/setup/complete`, end-to-end stage acceptance는 아직 실행할 수 없다. 요청 Host나 임의 기본값으로 이 경로를 채우지 않는다.
- `IssuanceService`에는 `Issue`/`Renew`만 있다. Reissue·series update/archive service 동작은 관련 HTTP route를 노출하기 전에 보완해야 한다.
- 4단계 첫 작업은 runtime에 Authority/Query를 조립하고 HTTP handler/DTO를 붙이는 것이다. 모든 state-changing route는 현재 세션·CSRF 검증을 거치며, 변경/생성은 If-Match·Idempotency-Key 규칙을 유지한다. 초기 URL 결정을 사용하는 Leaf 연동 검증과 전체 DB 장애·경쟁 검증은 후속 gate다.

## 3단계 구현 예정: 인증·설정·초기 화면

**기능:** 로그인/로그아웃/현재 세션 조회/비밀번호 reset 완료를 cookie 기반 HTTP 흐름에 연결한다. pre-auth CSRF와 session CSRF를 분리하고, setup/settings/dashboard 화면과 로컬 HTML/HTMX 자산을 제공한다. reset token을 URL/history에서 제거한다.

**재사용 모듈:** `service.IdentityService` (`IdentityDeps`: `PasswordHasher`, `TokenCodec`), `service.SettingsService` (`SettingsDeps`: `URLValidator`), `service.SetupService` (`SetupDeps`). 구현 타입은 `authcrypto.PasswordHasher`, `authcrypto.TokenCodec`, `contract.Identity*Command`, `contract.Settings*Command`다.

**의도한 결합:** HTTP handler → typed contract → service. Session middleware는 session cookie를 `IdentityService.Authenticate`에 전달하고 반환된 `Principal`만 보호 route에 사용한다. Settings handler는 `SettingsService`에 위임하며 DB/version/TLS URL 검사는 service/port가 소유한다. HTML은 explicit response DTO를 렌더링하고 DB·crypto engine을 직접 호출하지 않는다.

**미결정:** 설정 행이 없는 첫 설치에서 `service_url`을 입력할 API 경로가 없다. 요청 Host나 임의 기본값으로 대체하지 않고 PR에서 질문한다.

## 4단계 구현 예정: CA와 발급 API

**기능:** Root/Intermediate 생성·조회·상태 변경과 Leaf series/certificate 조회, issue/renew/reissue/update/archive를 OpenAPI에 연결한다. If-Match, Idempotency-Key, scope authorization, response/error mapping을 적용한다.

**재사용 모듈:** `AuthorityService` (`AuthorityDeps`), `IssuanceService` (`IssuanceDeps`), `QueryService`, `cryptoengine.KeyEngine`, `CertificateSigner`, `authcrypto.SerialGenerator`, `cryptoformats.ProfileValidator`/`ChainValidator`.

**의도한 결합:** HTTP adapter가 request metadata와 typed command를 만든다. Services는 key/signing/validation ports를 준비 작업에 쓰고, `UnitOfWork.Write` 안에서 최신 권한·version·domain transition·audit를 커밋한다. Handler는 SQL/dialect를 알지 않는다.

**선행 gap:** 현재 `IssuanceService` 공개 동작은 `Issue`와 `Renew`다. Reissue와 series update/archive 동작을 이 단계 route에 앞서 보완한다.

## 5단계 구현 예정: 다운로드·폐기·CRL worker

**기능:** public/private download link 생성, public CA certificate/chain/CRL route, atomic private GET sink, HEAD/Range/conditional 거부, 고정 filename, no-store와 writer deadline을 구현한다. Revoke/compromise/failure API와 CRL job worker를 lease/version/dedup/retry/shutdown 규칙대로 연결한다.

**재사용 모듈:** 현재 `DistributionService.Deliver`/`RecoverInterruptedTransfers`, `CRLService.RequestPublication`/`Publish`, `MaintenanceService.ExpireDeliveries`/`RecoverTransfers`/`PruneAudit`, `port.DownloadSink`, `JobRepository`, `CRLRepository`, `CRLSigner`, `RuntimeGate`가 있다.

**의도한 결합:** link handler → Distribution service, token GET → Distribution service → bounded `DownloadSink`; revoke handler → revocation service/common `applyRevocations`; worker → claimed `JobRepository` job → CRL service. Worker는 좁은 internal principal로 실행하고 HTTP adapter는 token/secret/payload를 로그하지 않는다.

**선행 gap:** `DistributionService.CreateLink`/`ReportFailure`, 별도 `RevocationService`, response sink adapter와 `internal/worker` loop는 없다. 공통 `applyRevocations` helper는 존재한다.

## 6단계 구현 예정: import·전환·TLS·감사 API

**기능:** import preview/commit과 CA key/takeover, transition/deployment confirmation, TLS candidate upload/reload/managed issue/activate, audit list/export routes를 연결한다.

**재사용 모듈:** `ImportService` (`ImportDeps`), `TransitionService` (`TransitionDeps`), `TLSService` (`TLSDeps`), `QueryService`; `cryptoformats.PKIParser`, `ChainValidator`, `CRLVerifier`; `tlsruntime.ConfigManager`.

**의도한 결합:** Multipart adapter가 크기·schema·unknown field를 검증해 typed command를 만든다. Import service가 parser/verifier/key/storage ports를 조정한다. Transition/TLS handler는 version/action/scope metadata를 전달하고 policy checks는 services에 남긴다. Audit export는 Query service의 권한 필터 결과만 JSON/CSV로 바꾼다.

**현재 상태:** Services는 존재하지만 일반 HTTP routes/UI가 없다. Runtime은 현재 TLS reload에 `unavailableTLSFileSource`를 주입한다.

## 7단계 구현 예정: 로컬 CLI·Unix socket

**기능:** reset link 발급, TLS reload/bootstrap recovery, rotate, restore-finalize, audit prune을 CLI에 연결한다. Online maintenance는 권한 제한 Unix socket, offline 동작은 동일 service와 execution lock을 사용한다.

**재사용 모듈:** `MaintenanceService` (`MaintenanceDeps`), `IdentityService.BeginReset`, `TLSService` internal operations. `cmd/cert-me`에는 현재 DB 명령과 `serve`만 있고 `internal/adapter/local`은 없다.

**의도한 결합:** CLI parser → secret-aware contract command → service → ports. Online socket은 runtime가 구성한 허용 service method만 노출한다. Raw SQL이나 lock 우회 경로를 만들지 않는다.

## 8단계 구현 예정: Docker·운영·B06 통합 종료

**기능:** non-root multi-stage Dockerfile/Compose, loopback host binding, persistent DB/key configuration, TLS proxy log/cache policy, initial fingerprint check와 restore/key rotation runbook을 제공한다. 전체 OpenAPI operation parity 및 initial HTTPS → admin/setup → CA → Leaf → key delivery → revoke/CRL 흐름을 네 DB에서 검증한다.

**현재 모듈:** 현재 저장소에는 Dockerfile/Compose, `internal/worker`, `internal/adapter/local`, static HTML/HTMX 자산이 없다.

**의도한 결합:** `cmd/cert-me` → `internal/runtime` → HTTP/local/worker adapters → application services/ports → SQL/crypto/TLS adapters. Container는 단일 `serve` process와 persistent state를 제공하고 proxy/host firewall 설정은 애플리케이션 인증 경계를 대신하지 않는다.

## 완료 기준

- OpenAPI의 공개 HTTP 입력·출력이 구현과 일치한다.
- 제한된 초기 HTTPS에서 관리자 생성과 설정을 끝낸 뒤 Root/Intermediate 생성, Leaf 발급, 개인키 수령, 폐기, CRL 게시까지 실행된다.
- 신뢰 프록시·Origin/CSRF·CSP·비밀 경로 로그 경계를 구현하고, 재시작/TLS 복구/일회성 전송을 검증한다.
- SQLite, PostgreSQL, MySQL, MariaDB에서 초기화·잠금·실패 복구 경로를 검증한다.
- 기본 Docker 공개 포트는 loopback에 바인딩하고 초기 설정 및 restore-finalize 운영 절차를 문서화한다.

## PR에 남길 질문과 문서 항목

- 초기 설정에서 `service_url`을 입력할 경로가 현재 API에 없다. 기본값이나 요청 Host를 사용하지 않는다. 사용자의 지시에 따라 PR에서 경로를 질문한다.
- `CERT_ME_TRUSTED_PROXY_CIDRS`의 쉼표 구분 형식, unset/empty 동작, 잘못된 CIDR의 시작 거부를 기존 운영 문서에 반영할 항목으로 남긴다. 임시 architecture 문장 수정은 되돌렸다.
- 실행 잠금 감시는 2초 polling, 최대 60초 검사 timeout이다. 연결 단절 시 fail-closed 및 두 번째 프로세스 잠금 경쟁을 네 DB에서 확인한다.
