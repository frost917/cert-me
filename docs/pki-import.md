# 기존 PKI 및 폐기 이력 가져오기

## 범위

초기 설정에서 새 Root 생성 또는 기존 PKI 가져오기를 선택한다. Root뿐 아니라 Intermediate·Leaf도 가져오기 대상으로 포함한다.

- Root·Intermediate 인증서와 개인키를 가져오고 유효성·폐기 이력·인수 검증을 완료하면 발급 및 CRL 서명을 활성화할 수 있다.
- Leaf는 인증서만 등록해 조회와 만료 관리에 사용한다. 일반 갱신에는 해당 발급 CA의 개인키가 등록되어 있어야 한다. 갱신 횟수는 등록 시 0부터 계산하며 가져오기 이전 키 사용 이력은 포함하지 않는다고 표시한다. 관리자는 첫 재발급부터 새 키를 선택할 수 있다.
- 이름 비교뿐 아니라 실제 서명과 CA 제약으로 체인을 검증한다.
- 암호화된 CA 개인키는 입력한 암호로 해제한 뒤 서버 암호화로 재암호화한다.
- 지원 형식과 체인 제한은 아래 지원 범위에 따른다. CA 인증서만 가져오는 이력 관리도 허용하되 서명·CRL 발행은 비활성화한다. Leaf 개인키는 가져오거나 보관하지 않는다.

## CRL 가져오기 확정 흐름

1. CA 인증서와 PEM 또는 DER CRL을 업로드한다. Root와 Intermediate는 각각 자신의 CRL을 등록한다.
2. 해당 CA 공개키로 서명을 검증한다. 발행 시각, 다음 갱신 시각, CRL 번호 및 지원하지 않는 확장을 확인한다.
3. 일련번호, 폐기 시각, 폐기 사유를 미리 보여준다. 등록된 인증서가 있으면 연결한다.
4. 관리자 확정 후 기존 폐기 기록과 합친다. 인증서 파일이 없는 항목도 보존한다.
5. 이후 cert-me가 발행하는 CRL에 가져온 폐기 정보를 반영한다.

폐기 항목은 CA와 일련번호의 조합으로 식별한다. 다른 CRL에 항목이 없다는 이유로 기존 기록을 삭제하지 않는다. 중복·상충 기록은 아래 중복·충돌 정책을 따르며 정정은 아래 지원 범위의 별도 정정 절차를 따른다.

MVP는 CA 전체 범위의 완전 CRL을 지원한다. Delta CRL과 범위가 분할된 CRL은 명확히 거부한다. 해석할 수 없는 중요 확장을 무시하고 가져오지 않는다.

CRL은 발행 시점의 폐기 목록이며 전체 감사 이력이 아니다. 만료된 인증서 등 과거 항목이 빠져 있을 수 있다. CRL만으로 과거의 모든 작업을 복원했다고 표시하지 않는다.

폐기 이력이 없으면 관리자가 명시적으로 '기존 폐기 내역 없음'을 선택한다. CRL 파일 부재를 폐기 내역 없음으로 자동 해석하지 않는다. 기존 이력 확인 전 빈 CRL로 대체하지 않는다.

## 중복·충돌 처리

가져오기 전 신규·중복·충돌 건수를 미리 보여준다. 충돌이 있으면 기본적으로 반영을 중단하며 자동 덮어쓰기를 하지 않는다.

| 상황 | 처리 |
| --- | --- |
| 완전히 동일한 인증서 재등록 | 기존 항목을 반환하고 중복 생성하지 않음 |
| 같은 발급 CA·같은 일련번호인데 내용이 다름 | 충돌로 거부 |
| 같은 이름이지만 다른 인증서 | 다른 충돌이 없으면 별도 항목 등록 |
| 기존 인증서와 같은 공개키를 쓰는 다른 인증서 | '중복된 인증서' 팝업을 표시하고 등록 거부 |
| 동일한 폐기 기록 재등록 | 중복 생성하지 않음 |
| 같은 인증서의 폐기 시각·사유가 다름 | 기존 기록 유지, 충돌 표시 후 관리자 확인 |

완전히 동일한 인증서의 재등록은 위 동일 항목 처리로 우선 판정한다. 공개키 중복 검사는 기존 등록 항목과 같은 가져오기 묶음 내 항목에 적용한다. 공개키 재사용 등록 거부는 가져오기 정책이며 일반 갱신에서 같은 공개키로 새 인증서를 발급하는 확정 정책을 변경하지 않는다. 장기 교차 서명 도입 시 필요한 가져오기 예외는 별도 설계한다.

## 만료된 CRL 가져오기

서명 및 기존 지원 범위 검증을 통과한 만료 CRL은 폐기 이력 가져오기용으로 허용한다. 미리보기와 결과에 만료 상태 및 '이후 폐기 내역이 누락됐을 수 있음'을 표시하고 최신 전체 이력으로 간주하지 않는다.

항목은 기존 폐기 기록과 합치며 누락 항목을 삭제하지 않는다. 해당 CA 개인키를 사용할 수 있고 CA가 만료되지 않았으며 CRL 발행 조건을 충족하면 반영된 이력으로 새 CRL을 발행하고 기존·가져온 번호보다 큰 번호를 사용한다. 만료된 원본 CRL을 현재 유효한 배포 CRL로 게시하지 않는다. CA 개인키가 없거나 CA 만료 등으로 새 CRL을 발행할 수 없는 경우에는 발행 불가 상태를 명시한다.

서명 불일치·지원하지 않는 Delta CRL·분할 CRL은 만료 여부와 관계없이 거부한다.

## 배포 연속성

가져오기는 기존 인증서의 CRL URL을 변경하지 않는다. 이전 주소에서도 새 CRL을 제공하도록 기존 경로를 유지하거나 라우팅을 구성해야 한다. 가져온 CRL 이후에는 기존 발행 번호와 가져온 번호보다 큰 CRL 번호를 사용한다. 기존 시스템의 발급·CRL 게시를 중지하고 최종 이력과 최대 CRL 번호를 확인한 뒤 cert-me 발행을 활성화한다. 발급 시 등록 인증서와 인증서 파일 없이 가져온 폐기 기록 모두에서 일련번호 중복을 검사한다. 미제공 과거 발급 이력의 중복 부재는 보증할 수 없으므로 이전 자료 확인 결과를 기록한다.

## 지원 범위와 반영 계약

- 가져오기 묶음은 검증 후 원자적으로 반영한다. 동일 인증서는 DER 기준으로 판정하고 공개키 중복은 정규화한 SPKI로 판정한다. Root 단독, Root → Intermediate, Root → Intermediate → Leaf를 허용한다. Root 직접 Leaf, 추가 Intermediate 계층과 교차 서명은 MVP에서 명확히 거부한다.
- 인증서는 PEM/DER, 개인키는 평문 PKCS#8·PKCS#1·SEC1 및 암호화 PKCS#8(PBES2, PBKDF2-HMAC-SHA256, AES-CBC 128/192/256)을 지원 범위로 둔다. 레거시 PEM 암호화·지원하지 않는 암호화 조합은 구체적 오류와 함께 거부한다. 실제 라이브러리와 상호운용 fixture 검증은 구현 담당자가 수행한다.
- 키 알고리즘은 [발급 프로필](./certificate-lifecycle.md)의 지원 목록과 동일하다. 만료 인증서는 이력 등록을 허용하되 발급 CA로 활성화하지 않는다. SHA-1/MD5 서명 인증서는 MVP import에서 거부한다.
- 상충하는 폐기 기록은 기존 값을 유지한다. 관리자는 충돌 항목을 제외하거나 원본 기록을 확인한 후 별도 정정 작업을 실행할 수 있다. 정정은 폐기를 해제하지 않고 사유·시각의 이전 값과 근거를 감사 기록에 남긴다. certificateHold/removeFromCRL 기반 임시 보류·해제는 MVP에서 지원하지 않는다.
- 가져온 폐기 시각은 외부 시스템의 시계로 기록된 값이므로 현재 시각 기준 검사 없이 원본 그대로 보존한다. 먼 미래 시각이 발견되면 원본을 유지한 채 관리자 검토 대상으로 표시하며, 시각을 이유로 폐기 효력을 늦추거나 기존 폐기를 제거하지 않는다. 관리자가 새로 실행하는 정정에는 [수명 정책](./certificate-lifecycle.md)의 `now + 5분` 허용치를 적용하며, 이는 복원 경로와 구분되는 별도 경로다.
- CRL 번호가 없는 입력은 운영자가 이전 최대 번호를 명시해야 발행을 활성화한다. 외부 기존 발급자는 먼저 발급·CRL 게시를 중단하고 최종 자료를 가져온 후 cert-me가 책임을 인수한다. 동시에 같은 CA로 발행하는 구성은 지원하지 않는다.

미리보기 후 반영 시에도 현재 DB를 기준으로 중복·충돌·체인 검증을 다시 수행한다. 미리보기 결과만 믿고 커밋하지 않는다. 동일 인증서 재등록에 새로운 CA 개인키를 제공한 경우 기존 인증서 항목을 반환하되, 키 일치·권한 검증 후 그 항목의 서명 키를 추가하는 별도 작업으로 처리할 수 있다. 이 경로는 공개키 중복 거부를 우회해 다른 인증서를 등록하지 않는다.

만료 인증서는 원래 유효 시점의 서명·계층 제약을 검증하여 이력으로 보존한다. 미등록 발급자는 같은 묶음으로 제공해야 하며 고립된 Intermediate·Leaf는 등록하지 않는다. 가져온 제약을 완화하지 않고 후속 발급에도 적용한다. 알 수 없는 중요 인증서 확장은 거부한다. 기존 인증서의 SAN·용도는 수정하지 않으며 갱신 시에는 현재 발급 프로필을 검증한다.


## import 자원·공개 기록 경계

암호화 PKCS#8은 복호화 전에 전체 ASN.1 소비 여부와 PBES2/PBKDF2-HMAC-SHA256/AES-CBC 파라미터를 검사한다. 반복 횟수는 1~2,000,000, salt는 8~64바이트, IV는 16바이트, 명시된 keyLength는 선택한 AES의 16/24/32바이트와 일치해야 한다. PRF 생략(SHA-1 기본값)도 허용하지 않는다. ciphertext는 양수·16바이트 배수이며 기존 개별 파일 4 MiB 한도를 넘지 않는다. 상한 초과는 라이브러리 KDF 호출 전에 422로 거부한다. 낮은 반복 횟수를 허용하는 것은 기존 키 import 호환성 목적이며 서버의 저장 암호화 정책으로 그대로 계승하지 않는다.

한 요청의 PBKDF2 반복 횟수 합은 4,000,000 이하로 제한하고 모든 파일의 사전 검증을 마친 뒤 해제한다. 큰 묶음은 운영자가 나누어 제출한다. 키 생성·PKCS#8 해제·PKCS#12 변환은 기존 프로세스 전체 semaphore 2개를 공유하고 대기 5초 초과는 작업 전에 503이다. timeout만 걸고 계산 goroutine을 방치하는 구현은 금지한다. 초기 수치는 작업량 상한이며 목표 응답 시간을 측정한 결과는 아니다. B05에서 상한 입력의 CPU/메모리를 측정해 출시 기준에 기록한다.

manifest와 인수 evidence는 [API의 명시적 공개 스키마](./api-contract.md)를 따른다. 입력/검증 결과/저장 DTO를 분리하고 서버가 공개 필드를 재구성한다. 기존 CRLDP는 인증서 원본에서 표시하며 운영자가 기존 경로 유지와 발급 자료 확인을 선언한다. 임의의 CDP/AIA/증거 URL을 서버에서 자동 조회하지 않는다. 기존 주소 유지 책임과 미제공 이력의 한계는 유지한다.
