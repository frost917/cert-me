# 개발 순서와 검증 기준

## 기획 결정 상태

MVP 정책은 주제별 문서에 통합했다. [문서 안내](./README.md)의 담당 문서를 구현 기준으로 사용한다.
추가 사용자 승인을 기다리지 않고 데이터 모델·API·마이그레이션·라이브러리 선정 및 구현 계획을 구체화한다. 세부 버전·도구 선택과 오류 복구 알고리즘은 개발 책임이며, 제품 동작을 변경할 때만 새 결정이 필요하다.

장기 기능은 교차 서명·ACME·CA별 관리자·태그 ACL·OCSP·Prometheus metrics다. ACME의 키 관리는 클라이언트 책임이며 MVP로 앞당기지 않는다.

## 개발 순서

[백엔드 구현 설계](./backend-implementation.md)의 계약을 기준으로 다음 단위를 구현한다. 상세 구조를 다시 기획하는 단계를 선행하지 않는다.

1. B01: domain 값 타입과 갱신·수령·계정·폐기/CRL 정책 및 테스트.
2. B02: command/result·port·UnitOfWork 테스트 대역·비밀 입력·오류 계약.
3. B03: 발급·수령 서비스와 공통 폐기 작업의 협력 검증.
4. B04: 나머지 관리자·CA·import·전환·CRL·TLS·조회·유지보수 서비스.
5. B05: 실제 SQL·crypto·TLS·runtime·마이그레이션 어댑터와 네 DB 테스트.
6. B06: HTTP/HTML·로컬 CLI·worker·Docker 통합 및 운영 문서.

## 필수 검증 기준

- rotate는 읽기 전용 기존·새 키 입력을 수용하고 외부 키 파일·환경변수를 수정하지 않는다.
- 재암호화는 CA·수령 대기 Leaf·내부 HTTPS 개인키 모두에 적용되며 키 쌍 자체는 유지된다. 실패 시 기존 저장 상태를 유지한다.
- 재암호화 중과 성공 후 새 키로 재시작하기 전까지 일반 요청을 처리하지 않으며 키 원문을 로그에 남기지 않는다.

- 가져오기는 동일 인증서를 중복 생성하지 않고 기존 항목을 반환한다. 같은 공개키의 다른 인증서는 중복 팝업과 함께 등록을 거부하되 일반 갱신의 공개키 재사용은 허용한다.
- 같은 발급 CA·일련번호의 다른 인증서는 거부하고 폐기 시각·사유 충돌은 기존 기록 유지 후 관리자 확인 대상으로 표시한다.
- 가져오기 미리보기에 신규·중복·충돌 건수를 표시하고 충돌 시 기본적으로 반영을 중단한다.

- 검증을 통과한 만료 CRL은 이력으로 가져오고 만료·이후 이력 누락 가능성을 표시한다. 만료 원본을 유효한 CRL로 게시하지 않는다.
- CA 개인키가 있고 CA 유효성 및 발행 조건을 충족하면 가져온 이력을 반영한 새 CRL을 발행하며, 그렇지 않으면 발행 불가 상태를 표시한다.

- 관리자 재설정 링크 발급 즉시 기존 세션과 일반 로그인을 차단한다. 링크 재발급은 기존 미사용 링크를 무효화한다.
- 링크 만료로 로그인 차단이 해제되지 않으며 비밀번호 변경 완료 후에만 새 비밀번호 로그인을 허용한다. 발급·재발급·완료는 토큰 원문 없이 감사 기록에 남는다.

- 개인키 수령 기한 변경은 새 발급 건에만 적용되고 기존 대기 건의 만료 시각은 유지된다. 기존 개인키의 기한 연장 경로를 제공하지 않는다.
- 대시보드에 개인키 수령 마감 시각과 남은 시간을 표시하며 만료 후에는 다운로드를 거부하고 기존 삭제·폐기 정책을 적용한다.

- Root·Intermediate 공개 인증서·CA 체인·CRL은 인증 없이 다운로드되며 목록·검색·관리 정보는 인증을 요구한다.
- CA 교체 후 이전 인증서 URL이 후속 인증서를 반환하지 않고 CA 개인키 다운로드 경로를 제공하지 않는다.
- 대시보드의 CA SHA-256 지문은 제공된 인증서와 일치한다.

- 갱신 인증서 저장과 횟수 변경은 원자적이며 실패·동일 요청 재시도·공개 인증서 재다운로드로 중복 증가하지 않는다.
- 키 교체 주기 변경 후 누적 횟수를 유지하고 다음 갱신 순번이 새 주기 이상이면 키를 교체한다.
- 가져온 Leaf는 갱신 횟수 0으로 등록하고 이전 이력 미포함을 표시하며 첫 재발급에서 새 키 선택을 지원한다.

- 공개 Leaf 다운로드 링크는 기본 10분 유효하며 유효한 GET 하나만 소비에 성공한다. HEAD는 소비하거나 파일을 반환하지 않는다.
- 새 공개 링크 생성 시 같은 인증서의 기존 미사용 공개 링크를 무효화한다. 유효기간 설정 변경은 기존 링크의 만료 시각을 바꾸지 않는다.
- 공개 다운로드 실패는 인증서 폐기를 유발하지 않고 새 링크로 재시도할 수 있다.

- HTTPS 교체 후보의 키 불일치·유효기간·용도·서비스 주소·체인 검증 실패 시 기존 인증서를 유지한다.
- HTTPS 교체는 새 연결에 적용하고 기존 연결을 유지하며, 재시작 후에도 마지막 적용 인증서를 사용한다.
- 외부 인증서 파일 변경만으로 적용 상태가 변경되지 않는다.

- 감사 기록 조회와 JSON/CSV 내보내기는 동일한 권한 범위를 적용한다.
- 보존 기간이 지난 감사 기록을 정리해도 인증서·폐기 정보 등 PKI 운영 데이터는 유지된다.

- SQLite·PostgreSQL·MySQL·MariaDB 각각에서 마이그레이션과 공통 저장소 통합 테스트를 실행한다. 동시 수령 요청 하나만 개인키를 반환하고 동시 갱신·CRL 번호 증가가 저장소 계약을 만족한다.
- 실패·재시작 이후에도 소비된 권한이 복원되지 않는다.
- 개인키 수령 후 일반 갱신은 서버에 Leaf 개인키 없이 가능하다.
- 서버 생성 방식은 갱신 3회째 키가 교체되고 이전 공개키와 구분된다. ACME에는 이 횟수 기반 규칙을 적용하지 않는다.
- 인증서 서명·체인·기간·용도 및 CRL 서명을 독립적으로 검증한다.
- CRL import는 다른 CA의 CRL, Delta CRL, 분할 CRL을 거부한다.
- 기본 CRL 재발행 주기는 12시간, 유효기간은 48시간이며 폐기 시 즉시 갱신한다. 재시작 시 놓친 재발행을 수행한다.
- 새 CRL 번호는 해당 CA의 기존 발행 번호와 가져온 CRL 번호보다 크다.
- 인증서가 없어도 가져온 폐기 항목을 보존한다.
- 초기 관리자 동시 생성에서 전체 관리자가 중복 생성되지 않는다. PKI 설정 완료 전에도 공개 가입 경로는 닫힌다.
- 관리자 재설정 링크는 비밀번호 변경 완료 시 한 번만 소비되고 기존 세션은 무효화된다. 단순 조회는 링크를 소비하지 않는다. 발급 후 3시간이 지난 링크로는 변경할 수 없다.
- 명시적 복구 절차가 기존 토큰·세션을 무효화하고 수령 대기 키를 삭제·해당 인증서를 폐기한다. 복구 정리 전 개인키 다운로드를 허용하지 않는다.
- 신규 발급 중지 CA는 갱신을 포함한 발급을 거부하되, 폐기 처리와 CRL 재발행은 계속 수행한다.
- 정상 CA 교체로 기존 인증서가 자동 폐기되거나 Leaf 키 교체 횟수가 초기화되지 않는다.
- Intermediate 유출 처리 시 부모 CRL에 해당 CA 폐기가 반영되고 영향받은 계층의 신규 발급·갱신이 차단된다.
- CA 유출 영향 상태와 개별 인증서 폐기 상태, 재발급 완료와 외부 장비 전환 완료를 구분한다.
- 긴급 전환 시 기존 갱신 횟수와 관계없이 Leaf 공개키가 변경되고 갱신 횟수가 초기화된다. 새 개인키는 일회성 수령 정책을 따른다.
- 기본 3시간이 지난 개인키 수령은 정리 작업 실행 여부와 관계없이 거부한다. 공개 인증서 다운로드에는 이 제한을 적용하지 않는다.
- 수령 실패·만료 후 관리자 실행 없이 새 키·인증서를 자동 발급하지 않는다.

장기 계획은 교차 서명, ACME, OCSP, CA 범위별 관리자, Prometheus metrics이며 MVP 완료 조건과 구분한다. 교차 서명을 위한 CA·키 세대·CA 인증서의 분리는 초기 데이터 모델에 반영한다. 정상 CA 교체는 병행 운영·순차 전환, Intermediate 유출은 부모에서 폐기 후 새 CA로 전환, Root 유출은 전체 계층 교체·기존 Root 신뢰 제거로 확정했다. 정책별 기준은 해당 주제 문서를 따른다.

## 보완 사항 검증

- 첫 관리자 생성 후 PKI 설정 실패·재시작에도 공개 가입이 다시 열리지 않고 기존 관리자가 설정을 재개한다.
- 키 수령 대기·전송 중 인증서의 갱신은 거부하며 동시 갱신이 계보를 분기시키지 않는다.
- 키 토큰 교체는 기존 기한을 유지하며 소비된 수령 권한을 복원하지 않는다.
- PKCS#12 변환 실패는 수령 권한을 소비하지 않고 암호를 저장하지 않는다.
- CRL 생성 완료 순서가 뒤바뀌어도 게시 번호가 후퇴하지 않고 생성 도중 추가된 폐기도 후속 CRL에 반영한다.
- HTTPS 메모리 적용 실패 시 DB 활성 버전도 복구하며 HTTPS 접속 불가 시 CLI로 교체할 수 있다.
- 보관 전용 CA의 키 부재는 복구를 막지 않고 실제 폐기 반영 대상 CA의 키 부재는 복구를 차단한다.
- import 미리보기 이후 동시 변경을 다시 검증하고 동일 CA 인증서에 서명 키를 추가할 수 있다.
- 저장 개인키가 없어도 잘못된 저장용 키로 시작하지 못한다.

## API·마이그레이션 계약 검증

- 동일 발급 요청 재생은 최초 성공 이후 ETag가 바뀌어도 기존 결과를 반환하며 개인키·토큰 원문은 재생하지 않는다.
- import 미리보기에서 개인키·암호를 영속 저장하지 않고 commit 재제출을 검증한다.
- 내부 CLI 비밀번호 복구는 로컬 서비스 경로 또는 오프라인 배타 잠금으로 실행한다.
- 네 DB의 DDL 중단·재개, 체크섬 불일치, 최신 스키마에 대한 구버전 실행 거부를 검증한다.
- 배타 잠금 소유 연결을 잃으면 다른 연결로 변경 작업을 계속하지 않는다.

## 후속 구현 참고: 저장소 실행 기반

이 항목은 백엔드 객체·서비스 구조가 확정된 뒤 수행할 저장소 작업이다. 목표는 네 DB에서 스키마를 안전하게 설치하고 중단 후 재개할 수 있는 CLI다. 상세 기준은 [실행기 설계](./storage-migrations.md#실행기-상세-계약)를 따른다. 웹 기능 구현은 이 기반의 검증 이후 진행한다.

1. `internal/config`: DB 종류·연결 정보·저장 키 env/file 입력 검증. 중복 설정·잘못된 길이 거부, 오류·로그에서 비밀 제거.
2. `internal/storage`: 전용 writer 연결과 읽기 풀 분리. SQLite 파일 잠금, PostgreSQL session advisory lock, MySQL/MariaDB GET_LOCK을 같은 실행 잠금 인터페이스로 제공. 소유 연결 상실 시 변경 작업 중지.
3. `internal/storage/migrate`: 000 journal bootstrap, 파일 체크섬·스키마 버전 확인, 순차 적용·상태 기록. MySQL/MariaDB는 실제 스키마 검사를 바탕으로 미완료 DDL 단계 재개.
4. `cmd/cert-me`: `db status`, `db migrate`, `db resume` 제공. 기존 DB의 자동 변경 없이 상태와 필요한 명령을 표시. 신버전 스키마·체크섬 불일치는 실패 종료.
5. 기존 CI를 확장해 네 DB에서 재실행·단계별 강제 종료·재개·두 프로세스 잠금 경쟁·소유 연결 단절을 검증.

완료 기준은 빈 DB 전체 설치, 같은 버전 무변경 재실행, 실패한 단계의 안전한 재개, 체크섬/스키마 불일치 차단, 동시 실행 한 개만 성공, 잠금 상실 후 쓰기 차단, 네 DB CI 통과다. 종료 코드는 성공 0, 입력 오류 2, 잠금 획득 실패 3, 스키마 불일치 4, 실행/복구 실패 5로 고정하고 비밀 없는 구조화된 결과를 제공한다.

이 단위가 완료되면 저장 키 verifier·임시 HTTPS 부트스트랩·첫 관리자 생성·세션·비밀번호 복구를 하나의 다음 개발 단위로 진행한다. 이후 CA 생성/import → Leaf 발급·일회성 수령 → 폐기·CRL → 대시보드·Docker 통합 순서다. ACME·교차 서명·범위별 관리자는 MVP 이후 계획을 유지한다.


## 보안 검토의 구현 완료 조건

SEC-01~06의 설계 선택은 [보안 검토 처리 결과](./security-review.md)에 확정했다. B01부터의 순서는 유지하며 별도 승인을 기다리지 않는다. B03에서 private 후처리 미확정 시 종료·시작 복구를, B04~B05에서 공개 import DTO와 KDF/저장 무결성을, B06에서 프록시 로그·출처·브라우저 방어와 초기 노출 예제를 완료한다. 문서/스키마 검증 통과를 실제 runtime 보안 테스트 통과로 표시하지 않는다.
