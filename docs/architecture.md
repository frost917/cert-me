# 제품 범위와 기술 방향

## MVP 확정 범위

- 여러 Root CA 및 각 Root 아래 여러 Intermediate CA 관리.
- 신규 발급 구조는 Root → Intermediate → Leaf의 3단계. 일반 관리 PKI에서 Root 직접 Leaf 발급과 추가 Intermediate 계층은 지원하지 않는다. 격리된 HTTPS 부트스트랩 CA에만 아래 예외를 적용한다.
- 서버 TLS 및 mTLS 클라이언트 인증서 발급·갱신·폐기.
- 대시보드 및 클라이언트에서 일회성 개인키 수령, 공개 인증서·체인 반복 다운로드.
- 기존 Root·Intermediate·Leaf 및 CRL 가져오기.
- CRL 생성·배포 및 감사 기록.
- Root·Intermediate 공개 인증서·CA 체인과 CRL은 인증 없는 고정 URL로 제공. CA 목록·검색·관리 정보는 로그인 필요. 공개 인증서 URL은 불변 인증서 ID를 사용하며 대시보드에 SHA-256 지문 표시.
- 초기 설정에서 서비스 기본 URL 지정. 인증서의 CRL 배포 지점에 사용한다.
- 자체 HTTPS로 대시보드·API·개인키 다운로드 제공.

## 기술 방향

| 영역 | 선택 |
| --- | --- |
| 백엔드 | Go, net/http |
| PKI | crypto/x509 중심, 암호화된 PKCS#8 처리는 검증된 라이브러리 선정 필요 |
| 화면 | Go html/template + HTMX |
| 브라우저 자산 | 일반 CSS, 필요한 부분만 TypeScript |
| 패키징 | 정적 자산을 Go 실행 파일에 포함 |
| API | REST, OpenAPI 계약 |
| DB | MVP에서 SQLite·PostgreSQL·MySQL·MariaDB 모두 지원, SQLite 기본 |
| DB 접근 | database/sql, DB별 쿼리 및 마이그레이션; sqlc 채택 보류 |
| 로그인 | DB 저장 서버 세션, HttpOnly·Secure 쿠키, CSRF 보호 |
| 실행 | Docker 단일 인스턴스, Compose 설치 예제 |

운영에 별도 Node.js 서버는 필요하지 않다. 라이브러리 및 도구 버전은 구현 착수 시 검증하고 고정한다.

서비스 로직과 HTML/API 핸들러, 저장소 구현을 분리한다. 저장소 인터페이스는 업무 작업과 트랜잭션 보장을 정의하며 서비스 로직에 DB 종류 분기를 넣지 않는다. 일회성 수령 권한 소비와 갱신 횟수 변경은 동시성 계약에 포함한다. SQLite·PostgreSQL·MySQL·MariaDB 모두 MVP에서 구현·검증한다. MySQL과 MariaDB도 각각 검증한다. 구체적인 지원 버전은 구현 착수 시 선정하고 고정한다.

PKI, 키 보관, 배포, 인증·권한, 백그라운드 작업을 단일 애플리케이션 안에서 모듈로 분리한다. CRL 재발행과 수령 만료 작업은 재시작 후 복구할 수 있도록 상태를 영속화한다.

## MVP 데이터베이스 지원

SQLite를 기본 설치로 제공한다. 외부 PostgreSQL·MySQL·MariaDB는 환경변수로 DB 종류와 연결 정보를 지정한다. DB별 마이그레이션을 제공하고 동일한 저장소 계약에 대한 통합 테스트를 각 DB에서 실행한다.

일회성 토큰 소비, 동시 갱신과 갱신 횟수 변경, CA별 CRL 번호 증가의 원자성과 일관성을 모든 지원 DB에서 검증한다. 실행 중 DB 전환과 DB 간 데이터 이전 도구는 MVP 범위에서 제외한다. 외부 DB 서버의 설치·백업 운영은 운영자가 담당하며 cert-me 자체는 단일 애플리케이션 인스턴스로 실행한다.

## 초기 설정과 권한

미설정 서비스는 계정 생성 화면을 바로 제공한다. 일회성 초기 설정 토큰은 사용하지 않는다. 첫 계정이 전체 관리자가 되며 첫 계정 생성과 공개 가입 종료를 원자적으로 처리한다. 완료 후 최초 관리자 생성 경로를 닫는다.

초기에는 전체 관리자 한 명이 관리한다. 장기적으로 Root CA 또는 Intermediate CA를 경계로 관리자 권한을 추가한다. CA 관리 권한과 다른 관리자에게 권한을 위임할 권한은 별도로 설계한다.

Leaf 재발급은 전체 관리자 또는 해당 Root·발급 Intermediate 범위의 관리자가 실행한다. 장기적으로 인증서에 태그를 부여하고 특정 범주의 인증서에 대한 ACL을 지원한다. 태그 기반 ACL의 상세 역할 매트릭스는 장기 기능 착수 시 설계한다. 태그 편집만으로 권한을 확대할 수 없도록 권한 변경과 일반 메타데이터 변경을 구분한다.

## 관리자 비밀번호 복구

운영자가 컨테이너 내부 CLI로 대상 관리자 계정의 비밀번호 재설정을 활성화한다. CLI에서 새 비밀번호를 지정하지 않고, 관리자가 대시보드에서 새 비밀번호를 입력해 완료한다. 기존 계정을 복구하는 기능이며 초기 설정을 다시 열거나 새 전체 관리자를 생성하지 않는다.

CLI 실행 시 대상 계정에 연결된 일회성 비밀번호 재설정 링크를 운영자에게 출력한다. 링크를 연 대시보드에서 새 비밀번호만 입력하여 변경한다. 별도 복구 코드 입력은 요구하지 않는다. 링크의 토큰은 서버에 해시로 저장하고 일반 접근·감사 로그에 원문을 남기지 않는다. 초기 계정 생성에는 토큰을 요구하지 않는 기존 정책과 별개다.

비밀번호 변경 완료 시 재설정 링크와 해당 계정의 기존 세션을 무효화한다. 토큰의 일회성 소비와 비밀번호 변경은 원자적으로 처리한다. 단순 링크 조회로 비밀번호를 바꾸거나 토큰을 소비하지 않으며 실제 변경 요청에서 소비한다. 링크로는 일반 관리자 작업을 허용하지 않는다. 재설정 링크의 유효기간은 발급 후 3시간이다. 만료된 링크로는 비밀번호를 변경할 수 없으며 내부 CLI에서 새 링크를 발급받아야 한다. CLI로 재설정 링크를 발급하는 즉시 해당 계정을 재설정 대기 상태로 전환하고 일반 로그인을 차단하며 모든 기존 세션을 무효화한다. 재발급 시 해당 계정의 기존 미사용 재설정 링크를 모두 무효화하고 새 링크에 발급 후 3시간의 유효기간을 적용한다. 링크 발급·재발급·비밀번호 변경 완료를 감사 기록에 남기며 토큰 원문은 제외한다.

비밀번호 변경 완료 시 해당 계정의 모든 재설정 링크와 세션을 무효화하고 재설정 대기 상태를 해제한다. 자동 로그인하지 않고 새 비밀번호로 다시 로그인한다. 링크 만료만으로 로그인 차단을 해제하지 않는다. 만료 시 운영자가 CLI로 새 링크를 발급받아 복구를 완료한다. 대기 상태 전환·세션 무효화·링크 교체는 동시 요청에서도 일관되게 처리한다.

## HTTPS와 감사

리버스 프록시가 있어도 애플리케이션 자체 HTTPS를 지원한다. 프록시에서 백엔드 인증서도 검증하도록 운영 문서에 안내한다.

초기 HTTPS는 CN이 `cert-me`인 Root 인증서를 생성해 부트스트랩한다. 이후 운영자가 인증서·키 파일을 제공하거나 대시보드에서 cert-me용 인증서를 발급하여 HTTPS 인증서를 교체할 수 있도록 한다.

부트스트랩은 임시 HTTPS 용도이며 실제 접속 DNS/IP를 수집하거나 인증서에 반영하는 것을 초기 구동의 조건으로 요구하지 않는다. 대시보드에 부트스트랩 임시 인증서 사용 상태와 운영 인증서로 교체하는 경로를 명확히 표시한다. 자체 생성 인증서는 클라이언트에 자동으로 신뢰되지 않으며 접속 이름 검증도 보장하지 않는다. 운영 인증서를 발급·설치할 때 실제 접속 DNS/IP에 대한 검증을 적용한다.

부트스트랩 CA는 일반 관리 PKI와 구분한다. 별도 임시 serverAuth Leaf를 직접 발급하며 Root와 Leaf 모두 30일 유효하다. 실제 접속 주소 입력은 요구하지 않는다. 운영 인증서로 교체한 뒤 부트스트랩 개인키를 삭제하고 공개 인증서와 교체 이력만 남긴다. 만료 시 자동 재생성하지 않으며 CLI로 명시적으로 재생성한다. 이 작업은 관리자 계정이나 초기 설정 상태를 초기화하지 않는다.

대시보드에서 발급하는 cert-me 자체 HTTPS 인증서와 개인키는 서버 내부에 설치한다. 개인키는 일반 Leaf의 일회성 수령 대기 데이터와 구분해 암호화 보관하며 HTTPS 제공과 재시작에 계속 사용한다. 일반 Leaf의 수령 기한·수령 후 삭제 정책에서 제외하고 다운로드 수령 경로를 만들지 않는다. 외부 제공 키도 검증한 스냅샷을 내부 암호화 저장한다. 자체 HTTPS 자동 갱신은 MVP 범위 밖이며 30일/7일/1일 만료 표시를 제공한다. 인증서 교체는 아래 무중단 적용 정책을 따른다. CA 개인키 다운로드 금지는 유지한다.

감사 기록에는 시각, 작업, 계정 또는 다운로드 토큰 식별자, 대상 인증서, 접속 IP, 성공·실패 결과를 포함한다. 발급 요청 계정과 인증서·개인키 다운로드 IP를 기록한다. 개인키, 토큰 원문, 해제 암호를 기록하지 않는다. 전달된 IP 헤더는 설정된 신뢰 프록시에서만 수용한다. 서버의 전송 결과와 클라이언트의 저장 완료를 동일시하지 않는다.

## 자체 HTTPS 인증서 교체

외부 파일 또는 대시보드에서 발급한 인증서를 교체 후보로 준비하고 다음을 검증한다.

- 인증서와 개인키의 일치 여부.
- 유효기간과 서버 인증 용도.
- 설정된 서비스 주소와 DNS/IP SAN의 일치 여부.
- 제공한 체인의 서명 연결과 구성.

검증 성공 시 인증서·키·체인을 한 묶음으로 재시작 없이 교체하고 새 TLS 연결부터 적용한다. 기존 연결은 유지한다. 임시 부트스트랩 인증서는 초기 구동 예외이며 운영 인증서 교체 후보에는 실제 서비스 주소 검증을 적용한다.

검증 또는 적용 실패 시 기존 인증서를 유지하고 대시보드 및 감사 기록에 원인을 표시한다. 개인키 등 비밀 데이터는 오류에 포함하지 않는다. 적용된 인증서와 키는 다음 재시작에도 사용 가능해야 한다. 후보 TLS 구성을 준비한 뒤 활성 버전을 DB에 커밋하고 메모리에 적용한다. 적용 실패 시 DB 활성 버전과 메모리를 모두 이전 버전으로 되돌린다. 복구 실패 시 서비스를 종료하고 유지보수 상태로 남긴다. 재시작은 정상 커밋된 활성 버전을 사용하며 미완료 교체 기록이 있으면 먼저 복구한다.

외부 파일은 변경 감지로 자동 적용하지 않는다. 대시보드의 '다시 불러오기' 또는 CLI 명령으로 명시적으로 반영한다. 재시작도 검증되지 않은 변경 파일을 자동 승격하는 경로가 되어서는 안 된다. 검증한 인증서·체인과 암호화한 키 스냅샷을 버전별 내부 저장하여 마지막 적용 상태로 재시작한다. 원본 파일은 수정하지 않는다. HTTPS가 만료되거나 주소가 변경되어 대시보드에 접속할 수 없는 경우에도 CLI로 운영 인증서를 검증·교체할 수 있어야 한다.

## 감사 기록 보존·조회 정책

- 기본 보존 기간은 1년이며 전체 관리자가 변경할 수 있다.
- 대시보드에서 기간·계정·CA·인증서·작업·IP·성공 여부로 검색한다.
- 검색 결과를 JSON 또는 CSV로 내보낼 수 있다. 내보내기에도 조회와 동일한 권한 범위를 적용한다.
- 초기 전체 관리자는 모든 감사 기록을 조회한다. CA 범위별 관리자 도입 시 해당 Root 또는 Intermediate의 관리 범위에 속한 기록만 조회·내보내기할 수 있다.
- 기록 수정·개별 삭제 기능은 제공하지 않는다. 보존 기간이 지난 기록만 자동 정리한다.
- 인증서 발급 상태·계보·폐기 정보 등 PKI 운영 데이터는 감사 기록과 분리해 보존한다. 감사 기록 정리가 CRL 항목이나 인증서 상태를 삭제해서는 안 된다.

감사 기록 내보내기는 DB 백업 데이터 내보내기와 별도 기능이다. 보존 기간과 정리 시점은 아래 설정 정책, 복수 CA 작업의 접근은 권한 확장 정책을 따른다.

## 저장용 암호화 키 교체

내부 CLI에 `rotate` 명령을 제공한다. 관리자가 기존 키와 새 키를 동시에 제공하면 백엔드가 기존 키로 저장 데이터를 복호화하고 새 키로 모든 저장 개인키를 재암호화한다. 대상은 CA 개인키, 수령 대기 Leaf 개인키, 내부 보관하는 cert-me HTTPS 개인키다. 인증서의 키 쌍 자체를 바꾸는 기능은 아니다.

명령은 주입된 환경변수·키 파일·외부 Secret을 변경하지 않는다. 읽기 전용 파일로 제공된 키도 입력으로 사용할 수 있어야 한다. 운영자는 재암호화 완료 후 배포 설정의 키 주입을 새 키로 전환하고 재시작한다.

교체 중 일반 요청을 중지하고 전체 재암호화가 성공한 경우에만 반영한다. 실패하면 기존 저장 상태를 유지한다. 재암호화 커밋 후부터 새 키로 재시작하기 전까지는 일반 요청을 재개하지 않는다. 재시작은 새 키로 저장 데이터를 사용할 수 있는지 검증한 후 서비스를 연다. 키 원문은 로그에 남기지 않고 교체 결과만 감사 기록에 남긴다.

기존 키를 분실한 경우 `rotate`로 복구할 수 없다.

- 저장용 키는 무작위 32바이트를 Base64로 전달한다. `CERT_ME_ENCRYPTION_KEY` 또는 `CERT_ME_ENCRYPTION_KEY_FILE` 중 정확히 하나를 지정한다. 누락·동시 지정·잘못된 길이는 시작 오류다. 파일은 같은 Base64 텍스트 형식이며 마지막 개행만 허용한다.
- AES-256-GCM으로 저장 개인키를 암호화한다. 암호화마다 새 nonce를 사용하고 레코드 ID·용도·형식 버전을 인증 부가 데이터로 묶는다. 키 식별자·암호문 버전을 저장하되 원문 키는 DB에 저장하지 않는다.
- rotate 입력은 기존 키 파일과 새 키 파일 또는 명명한 환경변수 참조를 지원한다. 키 원문을 명령행 인자로 전달하지 않는다. 읽기 전용 입력을 수정하지 않는다.
- 웹 서비스를 중지한 유지보수 실행에서 CLI가 동일 백엔드 로직을 사용한다. DB 잠금으로 서비스·다른 유지보수 실행의 동시 접근을 차단한다. 모든 재암호화와 키 세대 갱신을 단일 DB 트랜잭션으로 처리한다.
- 커밋 전 실패는 롤백한다. 커밋 후 새 키로만 시작할 수 있다. 운영자가 외부 키 주입을 변경하고 재시작한다. 완료 상태는 키 세대 ID로 확인하며 중단 후 이전·새 키로 상태를 확인해 재실행한다. 성공한 회전을 무조건 다시 적용하지 않는다.

서비스와 유지보수 CLI는 모두 동일한 배타 실행 잠금을 준수한다. 잠금은 연결 단절·프로세스 종료 후 복구 가능해야 하며 저장소별 구현으로 검증한다. 키 세대 ID만으로 올바른 키를 판정하지 않는다. 암호화된 검증 레코드를 저장하고 시작·rotate 시 인증 복호화로 검증한다. 저장 개인키가 없는 DB에서도 잘못된 키로 시작하지 못하게 한다. 검증 레코드 역시 같은 트랜잭션에서 재암호화한다.

## 백업 범위와 복구 처리

DB 백업의 실행·스케줄·보관·스냅샷·스토리지 운영은 운영자 책임이며 cert-me 기능 범위에서 제외한다. SQL 또는 JSON 데이터 내보내기는 선택적 후속 후보이며 MVP 필수 기능으로 확정하지 않는다. 내보내기를 도입할 경우 데이터 범위와 암호화된 키 포함 여부를 별도 결정하며 CA 개인키 다운로드 금지 정책과 구분 없이 예외 처리하지 않는다.

운영자가 외부에서 DB를 복원한 뒤 명시적인 복구 모드로 실행한다. 일반 재시작과 구분하며 복구 정리 완료 전 일반 요청을 받지 않는다. 복구 시 기존 다운로드 토큰과 관리자 세션을 모두 무효화하고 복원된 수령 대기 Leaf 개인키를 삭제하며 해당 인증서를 폐기한다. 재발급은 관리자가 새 키로 실행한다. CA 개인키와 내부 설치된 cert-me HTTPS 개인키는 수령 대기 데이터가 아니므로 이 일괄 삭제 대상에서 제외한다.

- 서비스 중지 후 명시적 restore-finalize CLI를 실행한다. 기존 토큰·세션 무효화, 대기 키 삭제·인증서 폐기를 먼저 커밋하고 CRL 발행 작업을 영속 큐로 처리한다. 단계별 상태로 재실행 가능하게 한다.
- 기존 공개 CRL 등에서 최신 번호를 확보하거나 운영자가 최대 번호를 지정해 복원된 DB보다 번호가 후퇴하지 않게 한다. 백업 이후 발급·폐기 이력 손실은 복구 모드로 재구성되지 않으므로 관리자가 자료 정합성을 확인해야 한다.
- 필요한 CA 키가 없거나 CRL 게시에 실패하면 복구 미완료로 남기고 일반 서비스를 열지 않는다. 유지보수 CLI에서 키·자료 보완 후 재시도한다. 외부 백업 운용은 범위 밖이다.

복구에서 무효화하는 토큰에는 비밀번호 재설정 링크도 포함한다. 재설정 대기 계정의 로그인 차단은 유지하며 CLI로 새 링크를 발급해 완료한다. CRL 복구가 필요한 CA는 이번 복구에서 폐기를 추가하거나 게시 재개가 필요한 운영 CA다. 단순 이력 보관용으로 가져온 서명 키 없는 CA 때문에 전체 복구를 차단하지 않는다. 저장 암호화 키는 운영자가 DB와 별도로 보관·주입한다.

외부에서 과거 DB로 교체한 사실을 서비스가 항상 자동 감지할 수는 없다. 일회성 수령 보호는 명시적인 복구 절차를 따른 경우의 보장이다. 과거 백업 속 개인키 사본의 삭제·보존은 운영자 책임이며, 백업 이후의 발급·폐기 이력은 이 정리 절차만으로 복원되지 않는다.

## 장기 계획

- 교차 서명 지원. Root 전환 시 기존 신뢰 경로를 활용할 수 있도록 교차 서명 인증서 생성 및 배포 체인 선택 기능을 후속 단계에서 제공한다.
- ACME 자동 발급·갱신. 주기적인 자동 재발급은 ACME를 기본 경로로 삼는다. MVP는 관리자 수동 발급·갱신과 일회성 다운로드 링크에 집중하며, 주기적 다운로드를 위한 별도 자동화 흐름은 추가하지 않는다. 클라이언트 생성 CSR 흐름을 수용하도록 발급 로직을 분리한다. ACME의 키 생성·보관·교체 주기는 클라이언트 책임이며 서버 생성 방식의 3회 갱신 키 교체 규칙은 적용하지 않는다. ACME 대상 인증서 종류·검증 방식은 후속 설계한다.
- OCSP 지원.
- CA 범위별 관리자 권한.
- 태그 기반 인증서 ACL. 특정 범주의 인증서에 대한 관리 권한을 부여한다.
- Prometheus metrics 제공. Prometheus에서 알림 규칙을 평가하고 Alertmanager로 전달한다.

## 교차 서명을 위한 데이터 모델 원칙

CA의 관리 식별자, 키 세대, 개별 CA 인증서를 구분한다. 동일한 CA 공개키에 자체 서명 인증서와 다른 CA가 서명한 인증서가 연결될 수 있도록 설계한다. 인증서의 발급자·일련번호·유효기간·폐기 상태는 개별 인증서에 귀속한다.

관리 권한의 소속 관계와 암호학적 신뢰 경로를 분리한다. 교차 서명으로 다른 CA에 관리 권한이 자동 위임되지 않는다. MVP의 신규 발급은 기존 3단계 정책을 유지하되, 저장 모델에서 신뢰 경로가 항상 단일 트리라고 가정하지 않는다.

교차 서명 생성과 복수 배포 체인 선택은 MVP 범위에 포함하지 않는다. MVP에서는 교차 서명된 기존 PKI의 import도 거부한다. 경로별 제약 검증, 체인 선택, 폐기 영향, 전환 종료 절차는 후속 상세 설계 대상으로 둔다.

## 설정과 로그인 기본값

- 서비스 전체 설정은 전체 관리자만 변경한다. 초기 MVP에 CA별 설정 상속은 도입하지 않는다. CA별 관리자는 후속 단계에서 자신의 범위 발급·재발급 작업을 수행한다.
- 개인키 수령 기한은 5분~24시간(기본 3시간), 공개 Leaf 링크는 1분~3시간(기본 10분), 키 교체 주기는 1~100회(기본 3회)로 설정한다. 설정 변경은 기존 링크를 연장하지 않는다.
- 세션은 유휴 1시간 또는 로그인 후 24시간 중 먼저 도달한 때 만료된다. 비밀번호는 12~128자, 조합 강제 없이 Argon2id 해시를 사용한다. 해시 파라미터는 런타임에서 검증해 버전과 함께 저장한다.
- 로그인·재설정 시도에는 계정 및 IP별 속도 제한을 적용한다. 기본 15분 내 실패 10회 이후 재시도를 제한하며 영구 계정 잠금은 하지 않는다. CLI 재설정에 의한 로그인 차단은 기존 합의대로 완료까지 유지한다.
- 감사 보존 기간은 30~3650일(기본 365일), 정리는 하루 한 번. 기간 축소는 다음 정리부터 적용하고 UI에 삭제 예상 범위를 보여준다.

첫 계정 생성 후 PKI 설정은 재개 가능한 별도 단계로 진행한다. 계정 생성 커밋과 동시에 공개 가입 경로를 닫고, 미완료 PKI 설정은 해당 관리자 로그인 후에만 계속한다. 서비스 URL은 HTTPS 절대 URL로 검증하고 요청 Host 헤더로 복구·다운로드 링크를 구성하지 않는다. URL 변경은 전체 관리자만 수행하며 이미 발급한 인증서의 배포 주소는 변경되지 않으므로 이전 주소 유지 책임을 안내한다.

## 권한 확장 및 구현 위임

- CA 전환 작업은 원본과 대상 CA 양쪽의 관리 권한을 요구한다. 복수 CA가 관련된 감사 기록은 모든 관련 범위 권한을 가진 사용자에게만 전체 내용을 제공한다. 초기 전체 관리자는 모두 접근 가능하다.
- 태그 ACL은 후속 기능이며 기본 거부·명시적 허용을 원칙으로 한다. CA 관리 권한 부여와 태그 편집 권한을 분리한다. 상세 역할 매트릭스는 해당 기능 구현 때 작성한다.
- DB 종류는 sqlite/postgres/mysql/mariadb로 구분하고 연결 설정은 env 및 비밀 연결 정보 파일을 지원한다. 설정 중복은 오류로 처리한다. 외부 DB TLS는 기본 서버 검증을 사용하며 명시적인 내부망 구성에서만 해제할 수 있다.
- 각 DB의 구체적인 버전·드라이버·마이그레이션 도구·PKCS#8/PKCS#12 라이브러리는 개발 착수 시 공식 지원 상태와 fixture 테스트를 확인해 고정한다. 이는 기획 재승인 대상이 아닌 구현 책임이다. 네 DB 모두의 CI 통과 없이 지원 완료라고 표시하지 않는다.
- API 경로·테이블 이름·작업 큐 구현·오류 코드·CLI 플래그는 개발 설계에서 정한다. 이 문서의 원자성·실패 처리·권한 계약을 바꾸는 경우에만 기획 변경으로 다룬다.


## 보안 검토 후 확정한 운영 경계

[보안 검토](./security-review.md)의 SEC-01~06을 기존 제품 정책 안에서 보완한다. 온라인 Root, URL 일회성 수령, 최초 계정 생성 화면, 3시간 재설정 링크와 운영자 주도 DB 복원은 유지한다.

- 최초 설정은 운영자가 제한한 관리망·방화벽·터널에서 수행한다. 기본 Docker 배포 예제의 호스트 포트는 loopback에 바인딩하며 LAN 공개는 운영자가 바꾼다. 애플리케이션은 컨테이너 내부 인터페이스에서 HTTPS를 제공할 수 있다. 초기 승인 토큰이나 실제 접속 SAN 입력은 추가하지 않는다. bootstrap 인증서의 SHA-256 DER 지문을 콘솔과 읽기 전용 CLI 상태에 표시하고 별도 신뢰 경로로 비교하는 절차를 제공한다. 지문 표시는 자동 신뢰나 이름 검증을 대신하지 않는다.
- URL 토큰의 비밀 경계에는 cert-me뿐 아니라 TLS 종단 프록시·access/error log·APM·trace·응답 캐시를 포함한다. 배포 예제는 `/download/`와 `/reset-password/` 하위 경로를 고정 라벨로 기록하며 query·Referer·본문·비밀 헤더를 기록하지 않는다. 잘못된 토큰/404도 동일하다. 일반 로그도 요청 원문 URI 대신 매칭한 경로 템플릿 또는 고정 unknown 라벨을 사용한다. 프록시의 해당 응답 캐시·디스크 버퍼링을 끈다. 외부 관측 도구를 연결한 운영자가 같은 규칙을 적용해야 한다.
- 신뢰 프록시는 `CERT_ME_TRUSTED_PROXY_CIDRS`의 명시적 CIDR 목록이며 기본은 빈 목록이다. RemoteAddr의 IPv4-mapped IPv6를 Unmap 후 비교한다. 비신뢰 peer이면 모든 전달 헤더를 무시한다. 신뢰 peer에는 X-Forwarded-For만 사용하며 최대 16개 IP/2 KiB, 중복 헤더·빈 값·IP가 아닌 값은 400으로 거부한다. peer에서 시작해 오른쪽부터 신뢰 hop을 제거하고 첫 비신뢰 주소를 클라이언트 IP로 선택한다. 모두 신뢰 주소면 가장 왼쪽 주소를 사용하며 별도의 비신뢰 원본이 확인됐다고 표시하지 않는다. 헤더가 없으면 RemoteAddr를 사용한다. Forwarded/X-Real-IP/X-Forwarded-Host/Proto는 주소·출처 판정에 사용하지 않는다. 프록시는 외부 입력을 제거/정규화해 신뢰한 체인을 작성해야 한다.
- 관리자 비밀번호 해시는 Argon2id v19, memory=65536 KiB, iterations=3, parallelism=1, salt=16바이트, 출력=32바이트를 초기 프로필로 고정한다. 프로세스 전체 비밀번호 KDF 동시 실행은 2개, 대기열은 두지 않고 초과는 503이다. 기존 계정/IP 시도 제한을 해시 전에 검사하고 admission 거부를 비밀번호 실패로 세지 않는다. 없는 계정은 같은 프로필의 dummy hash 비교를 사용하되 같은 실행 예산을 적용한다. DB 해시 파라미터는 지원 프로필 allowlist로 검증하며 임의의 memory/iteration을 실행하지 않는다. 성능 측정은 B05에서 기록하되 자원 부족 때문에 조용히 더 약한 프로필로 내리지 않는다.
- 온라인 프로세스·컨테이너 운영자와 주입 암호화 키는 신뢰 경계 안에 있다. 오프라인 Root/HSM, 외부 변조 방지 감사 저장소, 외부 rollback 감지 저장소는 MVP에 추가하지 않는다. 이 기능을 도입하려면 운영 모델을 별도 협의한다. 외부 DB 복원에는 기존 restore-finalize가 필수이며 DB 백업 운영 기능은 추가하지 않는다.
